# Integrations share commands and receipts, with per-request callbacks

Narriflow has three ways in: the browser API under `/api/*`, the MCP server for assistants, and the public REST API at `/api/v1` for automation hosts and developers. The browser API admits Clerk sessions only ([ADR 0009](0009-authenticated-request-policy.md)). MCP and REST both act for a credential, start the same paid work, and must agree on who may do what and when a retry is the same request.

- **One command table.** Each integration action is a canonical command (`submit_video`, `open_upload`, `generate_clips`, `create_clip_export`, …) with one Workspace capability and one application scope, in `packages/services/src/integration-admission.ts`. MCP tools and REST endpoints each map onto a command, and a parity test checks every command against its browser peer. Error codes are transport-neutral. MCP requires the `integrations.mcp` feature and REST requires `integrations.api`; both are Business-only.
- **Receipts follow the user, not the credential.** An Operation Receipt is keyed by Workspace, acting user, command, and the client's idempotency key. A retry after key rotation, or through the other transport, replays instead of starting duplicate work. Receipts store only credential-neutral facts: a prepared social post stores the intent and its digest, and the MCP adapter mints a continuation for whichever credential is calling. Signed continuations still bind to their credential, because they authorize one client's prepared intent.
- **Recipes resolve after the replay lookup.** Intake, generation, and upload requests may name a Recipe (`recipeId`) instead of sending Brand Profile, generation, and finishing settings inline; sending both is a validation error. The fingerprint holds the Recipe's ID and never its revision, and the Recipe is read inside the receipt's `prepare` step (an Upload Session's admission, for uploads), the same place Brand Profile defaults resolve. The accepted result records the Recipe ID and revision it used. An honest retry after the Recipe was edited, or deleted, therefore replays the original result instead of conflicting, while a new key sees the edit.
- **Derived keys where domain identities are UUIDs.** Upload Sessions and Workflow Runs keep their own UUID keys. Integrations derive them as UUIDv5 of the acting user, command, and caller key, so equal caller keys from different users never share work, and MCP and REST reach the same Upload Session.
- **REST is its own app.** `/api/v1` is a separate Next route and Hono app with an API-key principal; it is not in the browser declaration inventory, and the Clerk proxy lets it through. Routes are defined with `@hono/zod-openapi`, and the OpenAPI 3.1 document is generated from them. Changes within v1 are additive; breaking changes need `/api/v2`.
- **Callbacks are per request.** A request that starts an intake, generation, or export may include `callback.url`. The callback row is written in the same transaction that accepts the work: the receipt transaction, or the Upload Session's finalization intent. A worker loop observes Operation Status through the trusted read, freezes the event when the operation is terminal or unavailable, and delivers it at least once with Standard Webhooks signatures, retries, and redelivery. Each Workspace has one signing secret, rotated with a 24-hour overlap; every receiver holding it is trusted for the Workspace.
- **Outbound fetches are pinned.** `guardedFetch` connects to the exact addresses that passed validation, which closes the DNS rebinding window for callbacks and for ingest, RSS, render, and generated-media fetches. yt-dlp subprocesses are outside the guard; link intake's allowed hosts limit them.

## Considered options

We rejected keying receipts by credential, because rotation and transport changes created fresh namespaces that double-charged retries. We rejected mounting REST on the browser app, because its session-only policy and fail-closed inventory are the point of ADR 0009. We rejected Workspace-level event subscriptions and REST Hooks for v1: a per-request URL matches how automation tools wait (n8n's Wait node resumes on its own URL) and needs no subscription registry. [ADR 0014](0014-workspace-events.md) later added a pull feed for work no request started, which is not a subscription registry. Its amendment later added Webhook Subscriptions that read that feed. We rejected per-callback secrets, because receivers would have to learn a new secret per request; a shared Workspace secret with rotation is what Standard Webhooks libraries expect. We rejected making open finalize-free to simplify upload callbacks; browser resume depends on it, so a later finalize registers its callback idempotently instead.

## Consequences

New integration surfaces add a command or map onto an existing one, and inherit admission, receipts, and callbacks. A callback request is refused before work commits when the Workspace has no signing secret. Callbacks never carry media URLs; receivers call the API for Download Grants. OAuth bearer tokens, Zapier and Make apps, publishing through REST, and subscription management stay out of v1. REST and MCP can propose posts into a Publishing Queue ([ADR 0015](0015-publishing-queue.md)); a person accepts each one in Narriflow.
