# Authenticated Request Policy owns browser-session admission

Authenticated Request Policy is the deep application module for every browser-session Hono request, Server Action admission, server-rendered page admission, and workflow progress stream. Its single `execute` interface accepts an explicit signed-in, Workspace-capability, or active-Project admission requirement, plus optional actor- or Workspace-scoped rate limiting and strict untrusted input. It resolves signed-in identity once; Workspace and Project variants additionally resolve the active Workspace once. Policy order is authentication, required active Workspace, capability, rate limit, Project, input, operation. Every adapter receives either a value or a bounded typed failure with one request identifier.

Actor Scope never aliases identity. `actorUserId` is always the signed-in App User. `workspaceId`, `workspaceOwnerUserId`, role, access status, tier, personal-Workspace state, and selection-change state are separate facts. The active-Workspace cookie is only a selection hint; a current membership constructs scope. Project admission includes lifecycle and membership in one query. An absent, expired, purging, or inaccessible Project is concealed. A Project in another Workspace is disclosed only when the actor is a member there, and mutations require an explicit user-confirmed Workspace switch.

Signed-in admission is deliberately identity-only. Bootstrap flows such as onboarding, invite acceptance, and creating another Workspace must not inherit the capability or billing state of an unrelated active Workspace. Their actor value contains App User identity facts but no fabricated Workspace facts; Workspace and Project adapters retain the complete Workspace Actor Scope.

Hono, Server Actions, pages, streams, and browser presentation are adapters. Hono has an exhaustive route declaration inventory with exact capabilities and rate scopes. Server Actions and pages use the same admission result and preserve framework redirect/not-found behavior. Streams bypass ordinary request caching and reauthorize on the bounded heartbeat, emit at most one safe revocation control event, and close. Browser recovery classifies the shared stable contract while Upload Session, Studio Editing Session, billing, and publication modules retain their richer domain recovery.

Domain modules express expected operation failures through `ExpectedDomainFailure`: a catalog-derived stable code, a safe message, optional bounded details or retry guidance, and one transport-neutral semantic kind (`invalid`, `unprocessable`, `forbidden`, `payment_required`, `missing`, `conflict`, `rate_limited`, or `unavailable`). Domains do not choose HTTP statuses. The browser-session Hono adapter exhaustively maps those kinds to `400`, `422`, `403`, `402`, `404`, `409`, `429`, and `503`, respectively, then produces the shared authenticated response with the policy's request identifier. The response allowlist is `error`, `message`, `requestId`, and optional `issues`, `details`, or `retryAfterSeconds`; revision, retryability, stale-count, and similar operation metadata belongs under `details`.

Unknown exceptions are wrapped only to preserve the request identifier, logged with stable request, adapter, operation, actor, Workspace, declared Project, elapsed-time, and disposition fields, and never expose their message. Domain modules remain authoritative for ownership, quotas, revisions, persistence, rendering, billing, publishing, and intake lifecycles.

## Considered options

We rejected keeping per-adapter helpers because exact capability and Project rules had already diverged; method-based capability inference because Narriflow distinguishes viewing, editing, processing, downloading, publishing, social, brand, API, member, Workspace, and billing capabilities; owner-shaped request users because they erase who acted; a process-global authorization cache because membership and billing changes must take effect promptly; automatic Workspace switching because a failed mutation must not silently run elsewhere; and forcing webhooks, provider callbacks, MCP OAuth, API keys, or public shares through a browser-session trust model.

## Consequences

Adding a browser-session surface requires an explicit inventory declaration and policy adapter. Common authentication, capability, Project, rate-limit, and recovery behavior is tested at the policy interface rather than repeated in each handler. Successful domain response shapes remain owned by their existing modules. Public health, Stripe and provider webhooks, OAuth callbacks that establish identity, Clerk delivery, MCP OAuth, scoped API keys, and public sharing retain independent trust and replay models. Narriflow's pre-production policy removes the old Workspace-user shape and generic Project middleware in the same cutover; there is no legacy fallback.
