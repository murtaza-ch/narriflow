# Workspace Events are a pull feed written in the transaction that makes the change

[ADR 0013](0013-integration-surfaces.md) gave integrations per-request Completion Callbacks and rejected Workspace-level subscriptions. That leaves a gap: Autopilot creates work with no request, so an n8n flow, a Zapier trigger or a script can learn about an imported episode only by polling the project list. `WorkflowEvent` can't carry it, because its delivery targets are fixed and its rows cascade-delete with the Project. A Workspace Event is a durable, Workspace-scoped record that outside tools poll with a cursor. It is a pull feed; [push delivery](#amendment-push-delivery-with-webhook-subscriptions) reads the same log.

- **One append-only log per Workspace.** `WorkspaceEvent` holds an `id` consumers deduplicate by, a `seq` cursor unique within the Workspace, a `type`, a `version`, a `subject` of IDs only, and a unique `dedupeKey`. It has no foreign key to Project, so events survive Project deletion. A maintenance loop deletes rows older than 30 days.
- **Written in the transaction that makes the change, never best-effort.** `workspace-event.ts` is the only writer. A hook queues its event from inside the existing transaction and the transaction flushes the queue as its last act, so a rolled-back or retried attempt drops its events with it. The one exception is a transaction run by the Operation Receipt executor (manual publication confirmation, a refused generation start): it flushes inside `mutate`, and the executor then inserts the receipt and registers the callback before commit. That cannot form a lock cycle: the executor takes the request's identity lock before `mutate`, so a concurrent identical request waits there holding nothing, and the rows it inserts afterward are new, so no other transaction can hold them while waiting for the counter. The first types are `autopilot.episode_imported` (the RSS import transaction when a rule created the Project), `operation.finished` and `social_post.finished`. `social_post.proposed` joined them with the Publishing Queue ([ADR 0015](0015-publishing-queue.md)): the receipt that creates a proposal queues it and flushes inside `mutate`, like the other receipt-held events, and the proposal's ID names it. `grant.paused` and `grant.expired` joined them with Standing Grants ([ADR 0016](0016-standing-grants.md)): the first is queued by the transaction that pauses a grant, including the one that derives `social_post.finished` for a failed post, and the second by the sweep that expires it, each flushed as that transaction's last act. `finishing.finished` joined them with Finishing: it is queued beside a generation's `operation.finished` when that generation failed or was cancelled (Finishing skipped), and by the finishing worker's closing transaction otherwise, so each Generation Finishing row emits exactly one.
- **One event per terminal transition.** `operation.finished` fires when an Operation Status lineage becomes final: an Ingest Job failing, being cancelled or being refused its generation handoff; an Upload Session ending before its import (expired, aborted, failed); a generation settling, derived for just the lineage the settling run belongs to; an export becoming final or being cancelled; and Project expiry cancelling queued work. `social_post.finished` fires at every Social Publication Attempt settlement, the TikTok webhook, manual confirmation, and failed media preparation. A retried export has a new `retryCount`, and an uncertain Social Post that is rechecked and settles again has a new attempt `terminalAt`, so each outcome is its own event while a replay of one outcome is not.
- **Operation Status decides when an operation is finished.** `operation.finished` derives its state with `deriveGenerationStatus` and `deriveExportStatus`, the functions Operation Status reads, and names the operation with `encodeOperationId`. A Workflow Run settlement derives after its follow-up work is admitted, because a lineage isn't final while a drain run is still to be admitted. An export whose failed variant could still be requeued by its live run isn't final; its run's settlement queues it instead. An intake that handed off to generation finishes with it. A captioned video's generation ends with its single export: detection admits that export in the transaction that completes it and freezes its ID in the completion event, and the export's first final outcome is recorded once on the detection run. The generation reports that record, so a retry of the export emits a new `operation.finished` for the export but leaves the generation as first announced, and deleting the export does not flip it.
- **A dedupe key outlives its event.** Every key is claimed in `WorkspaceEventKey` before its event is written, and the 30-day purge never deletes keys. A later settlement of the same lineage, even years on, finds the key and writes nothing. Keys go with their Project, or with the Workspace when no Project existed yet.
- **The cursor is a counter row bumped by the flush.** `WorkspaceEventCounter` holds `lastSeq` per Workspace, the same pattern as `Project.workflowEventSeq`. The flush bumps it once by the batch size and inserts the batch, as the transaction's last locking statements (the receipt executor's own inserts above aside), and the row lock holds until commit. A second writer takes the next `seq` only after the first is visible: commit order is `seq` order, and a reader that has seen `seq` n never sees an event below n appear later. Because the counter is the last lock a transaction takes, it can't sit in a lock cycle with the Project, export and run rows, and a batch whose keys are all known skips it entirely. The counter doesn't live on `Workspace`, whose row existing `FOR UPDATE` locks already contend for.
- **One read path.** `GET /api/v1/events` and `narriflow_list_events` are the `list_events` command, which needs `content.view` and `projects:read`. An empty `types` list means every type. `social_post.proposed` and `social_post.finished` rows also need `publishing:read` and are filtered out, not refused, without it.

This amends ADR 0013: a pull feed for work no request started is in. Completion Callbacks stay, because n8n's Wait node resumes on its own URL.

## Considered options

We rejected making readers lag behind a safe horizon, because admission transactions run up to 20 seconds, so any fixed lag either exposes gaps or delays every event. We rejected a relay loop that assigns `seq` after commit, because local and Railway workers share the database and the loop would need its own lease. We rejected putting the counter on `Workspace`, because writers there already queue behind `FOR UPDATE` locks. We rejected reusing `WorkflowEvent`, for the delivery targets and cascade described above. We rejected publishing after commit, because a crash between commit and publish would drop the event, and database triggers, because they hide which transitions emit. We rejected a marker column on each domain row (the origin run, the Ingest Job, the export) in favor of one key table, because a marker on the origin run is written under the Project lock while the cancel command locks that row first, and a new write order on a critical path is the risk this design exists to avoid. We rejected taking the counter inside each hook, because a hook in the middle of a settlement takes it before the Project and export locks that settlement still needs, which deadlocks against any transaction that takes them first.

## Consequences

Each new event type adds its own hook, tests and docs in its own change instead of instrumenting every write site at once. Every Workflow Run settlement now also derives the generation lineage it belongs to, with read-only queries on runs, run events and renders, before it flushes; a run that no handoff named derives nothing. An intake that acknowledges a generation late waits for any in-flight settlement of that generation's speech-to-text or detection run, so exactly one side announces it. A hook only queues; every transaction that queues must end with a flush, which the Workflow Run lifecycle's transaction wrapper does for all of its commands, and other transactions do explicitly as their last act. The migration that adds `WorkspaceEvent`, `WorkspaceEventKey`, `WorkspaceEventCounter` and `ClipExport.retryCount` must be applied before this code runs, because every settlement writes them. Delivery is at least once and a transition emits once. The 30-day window means a poller that was down longer re-syncs from list endpoints. Events carry IDs and a version, never media URLs, so a subject changes only by adding a version. `operation.finished` for an Upload Session that ended before any Project existed has a null `projectId`.

One flush sits before later writes of its own transaction. When a `generate_clips` request asks for finishing on a generation that had already failed or been cancelled, the Project service flushes the skip's `finishing.finished` inside the receipt executor's `mutate`, and the executor then inserts the receipt and any callback registration. Those are new rows keyed by the request's own identity, whose advisory lock the request already holds, so they take no lock another transaction holds while it waits for the counter. A generation that finished successfully queues nothing there, and a flush with nothing queued doesn't touch the counter.

## Amendment: push delivery with Webhook Subscriptions

A Workspace can also subscribe HTTPS endpoints to event types. This is a subscription registry after all, but a small one that reads this log and reuses the callback delivery code; REST Hooks stay out.

- **A cursor per subscription.** `WebhookSubscription` holds the sealed URL, `urlHost`, the event `types` and `lastDeliveredSeq`. A worker claims a subscription with a lease, reads the next matching events after its cursor with `listWorkspaceEvents`, and sends them one at a time in `seq` order. The cursor moves only after a 2xx, so a crash between the answer and the update redelivers: at least once, in order. A failing endpoint holds back only its own subscription.
- **Callback delivery, reused.** Each POST is `deliverCallback`: the URL is validated with `assertCompletionCallbackUrl` and sealed like a callback URL, the Workspace's one signing secret signs it (with rotation overlap) in the Standard Webhooks format, the pinned `guardedFetch` connects, and `nextAttemptDelayMs` sets the retry delay. The event `id` is the `webhook-id`. Creating a subscription needs a signing secret (`callback_secret_required`).
- **One sender per subscription, at a time.** A worker claims one subscription right before draining it and, before every POST, renews its lease in a statement that also requires the cursor to be below that event. A worker whose lease lapsed while it was busy finds the row taken or the cursor passed and sends nothing. Lanes work different subscriptions and the tick has a time budget, so a slow endpoint holds one lane.
- **Disabling.** A subscription is disabled with a reason after 20 consecutive failures, on a `410`, or when its cursor falls behind retention. The creator is emailed. Re-enabling resumes from the cursor. If events expired meanwhile, the next drain skips to the oldest retained one, since failing the retention check again would trap the subscription.
- **Retention check.** Retention deletes a prefix of the log, so `oldest retained seq - 1` is the lowest cursor that has lost nothing, or the counter's head when nothing is retained. An idle pass moves the cursor to the head it read before the events, so a subscription to a rare type isn't disabled because expired events of other types left a hole.
- **Commands.** `list_webhooks` needs `content.view` and `projects:read`. `manage_webhooks` (create, delete, enable, test) needs `processing.consume` and `processing:write`, and creating with `social_post.finished` also needs `publishing:read`. A Workspace may have 10 subscriptions, one per URL. There is no update: delete and create again.

We rejected a relay that pushes after commit, because the log already is the durable outbox. We rejected delivering several events at once or a retry queue per event, because one cursor per subscription gives ordering with no second state to reconcile. We rejected a delivery log table for the first version; `lastAttemptAt`, `lastResponseStatus` and `lastDeliveredAt` on the row answer "is it working".
