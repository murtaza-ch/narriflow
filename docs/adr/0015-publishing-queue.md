# The Publishing Queue holds proposals as draft posts and takes slots under an account lock

Each Social Account can have weekly posting slots in the Workspace time zone, stored as JSON on the account (`postingSchedule`). Finishing, REST, MCP and people can propose a post: a Social Post in the `draft` status, which nothing used before. A person accepts it, and it becomes an ordinary scheduled Social Post in the account's next free slot. Proposals never publish on their own.

- **A proposal is a draft Social Post plus a `SocialPostProposal` row.** The row names the finished Clip Export variant, the assisted copy variant the caption came from, and who proposed it (`person`, `integration` or `finishing`). It also records `acceptedAt` and `acceptedByUserId` once a person accepts, and it stays after that as the post's provenance. The post has no `scheduledFor` and no Frozen Publication State, so it takes no slot. The publication scheduler claims only `scheduled` posts whose media is ready, and recovery needs an attempt and a frozen state, so neither can see a proposal. `publishing-queue.db.test.ts` proves it. Project expiry already cancels drafts.
- **Proposing is an Operation Receipt.** `propose_social_post` (`publishing.manage`, `publishing:write`) is a command like the others, so a retry through any transport replays. The post, its proposal row, the `social_post.proposed` event and the receipt commit together, and the event is queued and flushed inside the receipt's `mutate` like the other receipt-held events ([ADR 0014](0014-workspace-events.md)). Finishing proposes under a key derived from its row, the clip and the account, so a re-claim repeats nothing. A Workspace holds 200 proposals at once. The proposal's ID is the receipt's resource, the event's `socialPostId`, and, after acceptance, the scheduled post's ID, so everything handed out keeps naming the same post.
- **Accepting runs the existing prepare-and-schedule path.** It freezes the same intent with the same checks: export freshness, the Brand Profile approval gate, TikTok's creator settings. A TikTok proposal needs the person's per-post choices, which the accept form collects, so "Accept all" skips TikTok and says so. The post's idempotency key is `proposal-accept:<id>`, written when the proposal is made and kept when it is accepted. It is not a UUID, and UUIDs are all a client, assistant or integration can send as a key, so none can claim it first; scheduling anything else under it is a conflict. A retry after a lost response finds the post the first attempt made, whatever slot the queue would pick now.
- **The slot is chosen under a lock on the Social Account row, in the transaction that writes the post.** The admission carries a `slotQueue` instead of a time. The Social Post store opens a read-committed transaction, locks the account (`FOR NO KEY UPDATE`, which still admits the post's own foreign keys), reads the instants that active posts occupy, asks the schedule for the first free one, and converts the proposal's own Social Post in place: status, `scheduledFor`, the request hash and the frozen state. The conversion matches the caption the acceptance read before the lock, so an edit made meanwhile fails the acceptance with `social_proposal_changed` instead of being lost. A second accept waits on the lock, then finds the draft already converted and returns the first post's result, so two accepts never take one slot. A slot is occupied by a post at exactly that instant whose status is not `draft`, `cancelled` or `failed`. The request hash leaves the time out for a queued admission, so a retry is the same request however the queue has moved.
- **Slots are local times.** `posting-schedule.ts` walks calendar days in the Workspace zone and resolves each slot with `calendar-time.ts`, so 09:00 stays 09:00 across a daylight saving change. On the day a clock repeats a slot's time it takes the first occurrence; on the day a clock skips it, the slot moves to the instant it would have had.
- **Bulk scheduling can use the queue.** A batch with `scheduleMode: "queue"` gives each post the next free slot of its own account, by the same lock and transaction. A spread batch skips instants the account already occupies. Its times are chosen when the batch opens, so a post accepted in between can still share one.
- **Finishing can end in the queue.** `delivery: "propose_to_queue"` with `queueAccountIds` makes Finishing write copy for the accounts' platforms, then propose each usable picked clip to each account, in account ID order, with that platform's copy. Each account's outcome is recorded on the pick, so a refusal by one account doesn't stop the others and a re-claim doesn't try it again. The settings are refused when saved unless the saver can manage publishing, every account is active in the Workspace, and some chosen export format fits each account's platform; an integration also needs `publishing:write`. Accounts are checked again when the settings run; one that is no longer active gets nothing and the row ends `partial` with `queue_account_unavailable`.
- **Accept all works in batches.** One call accepts at most 25 proposals and returns where to continue, so a long inbox never outlasts a request.

## Considered options

We rejected a unique index on (account, time) because manual and bulk scheduling put several posts at one time on purpose, and a partial index would still not choose the next slot. We rejected taking the lock around the whole admission with a nested connection because the pool could starve with every connection waiting for a second. We rejected a serializable transaction for queued admissions because its snapshot is taken before the lock wait and would not see the post that held the lock. We rejected deleting the draft and creating a new post: the proposal's ID, which REST and MCP had returned and the receipt and event named, would then point at nothing, and nothing would link the post to who proposed it. We rejected a separate table for slots: a JSON column is read with the account and edited as a whole. We rejected letting REST or MCP accept, because acceptance is the approval step the Brand Profile's rule exists to keep with a person. A person can delegate acceptance for one Autopilot rule through a Standing Grant ([ADR 0016](0016-standing-grants.md)), which runs this same accept path and never overrides the rule.

## Consequences

The migration adds `SocialAccount.postingSchedule`, `SocialPostProposal` and an index on (`socialAccountId`, `scheduledFor`); apply it before deploying. `social_post.proposed` needs `publishing:read`, like `social_post.finished`. Proposals appear in a project's posts as Draft, and cancelling one from there rejects it. The `SocialPostProposal` row of an accepted post is kept for as long as the post. Recovery's `cancel` action and the Calendar's list already handle `draft`.
