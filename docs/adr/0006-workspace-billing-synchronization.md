# Workspace Billing owns provider synchronization and access projection

One Workspace Billing Account stores the provider identity, verified subscription snapshot, reconciliation health, and retry ownership for one Workspace. The Workspace Billing module owns signed Stripe delivery acceptance, current-state retrieval, subscription policy, retention transitions, access projection, audit transitions, and due reconciliation behind one interface. Hono, the worker, Postgres, Stripe, the clock, and diagnostics are adapters. Stripe deliveries are notifications and never set entitlements from their payloads.

`Workspace.pricingTier` and `Workspace.status` remain the projection read by product modules. Only Workspace Billing changes that projection because of provider state. The module commits the billing snapshot, Workspace projection, Project retention changes, and append-only transition together. Claims use an immutable reconciliation attempt ID and an expiring lease; every settlement is fenced. Provider outages and catalog conflicts retain the last verified access.

## Considered options

We rejected User-level billing because one person may have different entitlements in different Workspaces; event-time ordering because Stripe delivery order is not current subscription truth; direct webhook tier writes because delivery retries and equal-second events can reverse access; a generic job framework because billing claims have their own provider and policy facts; and exposing Stripe or persistence adapters to callers because that would make callers reproduce reconciliation sequencing.

## Consequences

The public interface starts and resumes Checkout, observes Checkout returns, opens the portal, accepts a delivery, reconciles current or due accounts, reads a product billing view, and provides identifier-safe operator inspection. The production Stripe adapter retrieves the customer and the complete bounded subscription collection. Personal Workspaces fall back to active Free when paid access ends. Collaborative Workspaces with non-owner members become restricted on Free. Restricted access preserves owner billing, viewing, downloads, Viewer invitations, demotions, and removals while blocking edits, processing, publishing, API and MCP use, and new billable collaboration.

## Amendment — 2026-10-26: Checkout slot, recoverable subscriptions, and below-Business teams

Two client idempotency keys could previously open two subscription Checkouts for one Workspace, and a Free projection after past-due grace was taken as proof that no subscription could still bill. Workspace Billing now holds at most one open subscription Checkout per Billing Account in a unique Checkout Attempt slot, taken before any provider call and fenced at session binding. A different key for the same choice resumes the open session; a different choice is refused as `checkout_in_progress`. Before offering a session, the module retrieves the provider's subscriptions and routes any subscription that is not canceled or incomplete-expired to the portal, independent of the projected tier. We rejected a Workspace-level advisory lock held across Stripe calls, because a network call must never hold a database transaction, and expiring the older session on a conflicting choice, because it races a payment in progress.

Seat convergence runs only on subscriptions that can still bill, and a seat failure no longer blocks the verified projection; otherwise an ended plan or the start of past-due grace could wait behind a rejected seat change indefinitely. Projection commits take the Workspace usage lock before Project and billing rows.

The restriction rule is now plan-based rather than Free-only: a Workspace whose plan lacks team members and still has non-owner members, Viewers included, is restricted until the owner upgrades or removes them. A Workspace without non-owner members is unaffected. The restricted owner keeps billing, viewing, downloads, demotions, and removals; Viewer invitations while restricted are no longer allowed, because every new member requires the `workspace.members` plan feature. Plan changes stay in the Stripe portal configured with a single plans product; see the Workspace Billing runbook for the required configuration and the test-mode verification that payment-dependent upgrades must pass before launch.

## Amendment — 2026-10-27: Payment-gated plan changes and scheduled downgrades

The portal-only plan-change decision is superseded by verified provider constraints. Stripe rejected the proposed six-price single-product portal catalog because a product cannot expose multiple choices for the same billing interval. The portal also cannot update Business subscriptions containing a separate seat product. Per-target portal configurations would add configuration while still leaving those subscriptions and scheduled-change management without a complete path.

Workspace Billing now owns one quoted plan-change flow. Immediate upgrades use Stripe pending updates with immediate invoicing; scheduled downgrades use two-phase Subscription Schedules. A durable immutable quote and the existing Billing Account claim serialize confirmation and provider mutations. The owner sees the actual charge before confirming. Current-state reconciliation remains the sole entitlement writer, so pending payment retains the old plan and existing monthly credit usage. The portal owns invoices, payment methods, and period-end cancellation.

Only Narriflow-owned schedules may be replaced or released. The existing seat-convergence path also maintains future Business phases from committed membership. This prevents a seat removed before renewal from being charged again when the scheduled interval begins. We rejected optimistic tier writes, changing subscription prices with payment behavior that applies unpaid upgrades, a second Checkout for existing subscriptions, and rollout flags for this pre-production cutover.
