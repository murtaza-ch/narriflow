# Workflow Runs own one fenced lifecycle

Workflow Runs, but not Ingest Jobs, are owned by one deep lifecycle module. Each execution claim is itself an explicit `WorkflowAttemptRef`, with an immutable Workflow Attempt ID and renewable lease stored on the run. Workers pass that reference to every stage entrypoint and lifecycle command; dub rows inherit that attempt. Clip rendering uses the settled child-lease exception below. External-provider waits use an explicit lease-free `waiting` state, aggregate stages may terminate as `partial`, and the existing Workflow Event record is also the transactional outbox and replay source. This keeps one source of ownership truth and prevents a reaped worker, event-delivery failure, or telemetry failure from reversing newer domain state.

## Considered options

We rejected a generalized ingest/workflow job module because their lifecycles and payloads differ; a separate Workflow Attempt table because it would add a second state model without improving fencing; long provider leases because no worker exists to renew them; uncoordinated child leases because they create competing ownership truth; and a second generic outbox table because Workflow Event already provides durable ordered replay. We also reject protocol-versioned bridge workers: Narriflow's pre-production policy has no production data or mixed-version deployments to protect, so a V1/V2 split would preserve obsolete writers and weaken the ownership boundary without a real compatibility requirement.

## Consequences

`WorkflowRunLifecycle` is the sole externally visible Workflow Run write interface. Prisma and transaction construction remain private to the lifecycle services; claims always return a non-null attempt identity; and stage entrypoints receive both that exact attempt and their execution context without ambient storage. Worker adapters must treat `WorkflowAttemptLost` as a control signal rather than a workflow failure. `IngestJobLifecycle` separately owns source intake claims, progress, heartbeat, settlement, reaping, manual retry and the generation handoff. It commits Project state and the existing Workflow Event outbox in the same transaction, including terminal notification intent. Ingest events name `ingestJobId`; Workflow Run events name `workflowRunId`. Generation handoff uses Workflow Run admission to commit its run, transcript and Ingest Job acknowledgment together. Graceful worker shutdown releases the Ingest Claim and refunds that execution claim's automatic retry budget; expired leases still count as failed attempts.

Pending, unassigned Clip Render Variants are rescued through `WorkflowRunLifecycle.rescuePendingClipRenderingRun()`. The Project admission lock protects the recheck, run admission, Workflow Event and queued Clip Export linkage in one transaction. Pending variants already assigned to a terminal run do not create another rescue obligation.

Project progress uses active Workflow Runs before terminal history, then descending update time and run ID. Workspace Library SQL and Project detail snapshots use that same ordering. Pure progress and stage projections live in validators; the detail header and processing checklist consume the same stage facts. A current stage's run outcome takes precedence over artifacts from an earlier run. Browser SSE merging remains in the web adapter and fences events to the current Workflow Run.

## Render Group exception, 2026-10-29

The parent-only clip-rendering lease serialized every clip in a project on one replica. A process crash also charged the whole parent execution even when only one clip had started. Independently claimable Render Groups now partition the fixed Render Work Set by clip and frozen export configuration. There is still one parent Workflow Run, one public progress stream and one transactional outbox. This deliberately revises the original rejection of every child lease, without changing ownership for other stages.

`WorkflowRunLifecycle` retains parent admission, fixed membership, coordinator claiming, progress, cancellation, final settlement, follow-up admission and notification authority. The Render Group lifecycle owns group claims, heartbeats, execution starts, variant writes, group retries and reaping. It is the only child mutation authority after integration. A coordinator claim does not claim the encoder and does not renew, steal, reset, or charge child leases.

The coordinator allocates `renderWorkSetGeneration` once when freezing membership. It survives every coordinator reclaim and remains stable for that run. Groups reference that exact generation. A new work set uses another Workflow Run; late variants enter the existing idempotent drain follow-up. Explicit cancellation or editor supersession invalidates affected membership and fences its writes in the same transaction. Superseding one automatic variant does not invalidate frozen export variants or unrelated groups.

Every child write requires an open `clip_rendering` parent in `queued` or `running`, matching generation and group membership, an uninvalidated member, and the group's current token, owner and strictly unexpired DB-time lease. The parent's coordinator attempt and lease are absent from this predicate. Coordinator mutation still requires its own current Workflow Attempt. Transactions lock the project admission row when needed, then parent, group, member and variant rows in deterministic ID order. Cancellation and reaping take the same locks. Recheck DB time after acquiring locks, using `clock_timestamp() AT TIME ZONE 'UTC'`, rather than a process clock or a transaction-start timestamp that may predate a lock wait. A parent reaper may reclaim coordination while healthy child leases continue.

Parent settlement waits for a complete partition and terminal or superseded groups, no live child lease and no scheduled retry, including retries already due. Expired running groups must be reaped first. Counts, terminal Workflow Event, notification intent and late-work admission commit together under the coordinator fence and project admission lock. A duplicate settlement returns the committed outcome; a group never sends the parent's notification.

Migration `20261029160000_render_group_leases` is additive: a nullable parent generation, new tables, indexes and constraints. It can be applied while pre-group API and worker code runs, because that code never populates the new model. Deploy the schema/contracts, service protocol and worker integration together only after draining the old render workers. Applying this migration alone does not enable a second execution path or authorize shared-environment deployment.
