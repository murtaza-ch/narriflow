Review API handoff for ticket 28

- `createReviewsClient(boundTransport)` is the internal Clerk/Workspace client. All seven internal POST commands require a per-intent `Idempotency-Key`, supplied via Hono call options `{ headers: { "Idempotency-Key": key } }`. Keep the key through uncertain failures. Read `projects[":id"]["review-rounds"]` with `reviewQueries.room`.
- `createGuestReviewsClient({baseUrl,getSession,onSessionRefused})` is independent of Clerk. It omits cookies, supplies only the current guest Bearer, uses typed `ApiError`, and has no automatic retries or token refresh.
- Both `POST review[":token"]` and `.access` take the existing identity/email/passcode input and return `{sessionToken,expiresAt}`. Ticket 28 stores this only in tab sessionStorage under the review token's SHA-256 digest, clears it on expiry/refusal, and obtains fresh access explicitly.
- Guest comment/decision POSTs require caller keys and return the immutable original safe result on replay, with `Idempotent-Replayed: true`. Edits/deletes use their existing guarded operations and do not automatically retry.
- `reviewQueries.guestRoom`, `.media`, `.share` and `.optOut` take a SHA-256 digest separately from the raw URL token. Raw credentials never enter query keys. Guest cache keys have no Clerk/Workspace prefix.
- Media/download GETs return `{url,expiresAt}`. Assign the storage URL directly without a guest/Clerk header. Refetch before expiry and after tab resume. Public share GET returns the existing safe export DTO with completed downloadable variants only and a conservative 60-second `expiresAt`; refetch then. Nothing is persisted or dehydrated.
- `review["opt-out"].$get({query:{token}})` previews only. `$post({json:{token}})` explicitly confirms and is naturally idempotent. The email URL remains `/review/opt-out?token=...` on WEB_ORIGIN.
- After confirmed acceptance, use `invalidateReviewMutation` or `invalidateGuestReviewMutation`. No automatic mutation retries. The caller owns the per-intent key and successful completion.
