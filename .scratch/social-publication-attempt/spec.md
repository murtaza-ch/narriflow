# Deepen the Social Publication Attempt

**Status:** ready-for-agent

## Problem Statement

Narriflow can currently lose the distinction between a post that definitely failed and a post that a provider may already have accepted. A worker claims a Social Post by changing its status, performs a long provider-specific sequence, and writes the provider receipt only after the whole sequence returns. If the process, network, or database fails after the provider accepts the post but before Narriflow stores the result, the reaper eventually marks the Social Post failed. A user can then retry it and publish the same content twice.

The same shallow protocol causes adjacent correctness failures. Claims have no immutable ownership token, so a stale worker can settle work after another worker takes over. Provider operation identifiers are kept only in memory. Provider processing is polled while a worker remains occupied. Every exception becomes a terminal failure even when the provider reports a pending result or Narriflow lacks enough evidence to decide. Social Post settlement and analytics are separate writes, so a later analytics error can overwrite a successful publication with failure. The publisher also selects a completed clip render at execution time, which means a retry may send different bytes from those the user scheduled.

The product UX mirrors these ambiguities. It shows one generic Publishing state, turns stalled work into Failed, and offers an ordinary Retry action without warning when a duplicate is possible. Operators have no durable attempt history, provider checkpoint, stale-claim evidence, or safe reconciliation command. The five native providers and the publication webhook therefore repeat one fragile protocol without a module that owns its rules.

## Solution

Give each Social Post a durable sequence of Social Publication Attempts. A Social Publication Attempt owns one frozen publication intent and at most one provider-side publication operation. Its deep module accepts an owned attempt and an abort signal through one `execute` interface. It owns provider preparation, upload, submission, checkpoint persistence, receipt normalization, pending-provider reconciliation, retry classification, claim fencing, Social Post projection, analytics intent, diagnostics, and cleanup.

Scheduling freezes the exact completed Clip Export Variant, caption, account, platform settings, and capability version that will be published. A worker may refresh expiring credentials or media access without changing those inputs. Every provider adapter returns one of four normalized outcomes: accepted, pending, failed, or unknown. Pending work releases the worker and becomes due for later reconciliation. Unknown work is reconciled where the provider exposes exact evidence and otherwise becomes Needs attention. Narriflow never starts another provider publication operation merely because it did not receive the previous response.

Definitive pre-submission failures may retry automatically with bounded backoff. A new Social Publication Attempt is created only when the previous attempt is known not to have published and another attempt is safe. An accepted result, durable provider receipt, Social Post projection, and analytics intent settle atomically. Expired claims are recovered according to their last durable phase; they are not converted blindly to failure.

The user sees truthful states for preparing media, scheduled, publishing, provider processing, checking the outcome, published, failed, needs attention, and cancelled. Failed means Narriflow knows the provider did not publish. Needs attention means Narriflow cannot prove whether it did. That state offers Recheck, Confirm published, and Publish again with a specific duplicate-risk confirmation. It never shows the ordinary Retry action.

## Implementation Decisions

- Add Social Post, Social Publication Attempt, Publication Claim, Provider Receipt, and Frozen Publication State to the domain glossary. Social Post is the user's publication intent and current product projection. Social Publication Attempt is one durable provider operation for one frozen intent. Publication Claim is temporary worker ownership of that attempt. Provider Receipt is durable evidence returned or recovered from a provider.
- Record the ownership decision in an ADR. The Social Publication Attempt module owns claim-sensitive execution, provider checkpoints, normalized outcomes, reconciliation, retry eligibility, settlement, and publication diagnostics. Scheduling owns admission and frozen intent. Provider adapters own provider protocol details. The worker owns polling cadence only through module configuration and does not choose transitions.
- Use the approved primary interface: the attempt module executes one owned Social Publication Attempt with an abort signal. The caller supplies no media-selection, provider-phase, upload, submission, reconciliation, retry, settlement, analytics, or cleanup sequencing.
- Keep provider, persistence, media access, credential, clock, and diagnostic seams internal to the module. The platform seam is real because it has five native adapters, one webhook adapter, and a deterministic contract-test adapter.
- Scheduling uses a workspace-scoped client idempotency key. Replaying the same immutable input returns the original Social Post. Reusing the key with different account, platform, media, caption, schedule, or provider settings returns a typed conflict.
- Freeze one exact Clip Export Variant before a post becomes eligible for provider submission. The frozen state contains the export and variant identity, editor revision and fingerprint, storage identity, byte length, aspect ratio, caption, provider settings, account identity, platform, capability version, and schedule facts. Access tokens, signed URLs, and refreshable media locations are not frozen.
- If no matching immutable export exists, scheduling creates or reuses the current Clip Export request and projects Preparing video. The Social Post becomes Scheduled only after the exact variant completes. Export failure becomes a media-preparation failure and never consumes a provider attempt.
- Retain the exact export object while any nonterminal Social Post references it. Project deletion and retention purge must refuse or defer destructive cleanup while an attempt is publishing, processing, reconciling, or needs attention.
- Store Social Publication Attempts separately from Social Posts. An attempt stores immutable lineage, attempt number, prior-attempt link, current phase, normalized provider outcome, failure code and disposition, next action time, provider-call count, processing deadline, terminal facts, and timestamps.
- Each claim writes a new immutable claim ID, claimant identity, lease expiry, and heartbeat. Every checkpoint and settlement compares both attempt ID and claim ID. Ownership loss is control flow and changes no publication result.
- An expired claim never directly fails a Social Post. Recovery clears or replaces the claim and resumes from the last durable phase. A stale worker may complete a provider request but cannot overwrite the newer claim; the current claimant reconciles the durable provider operation.
- Use database-backed keyset claiming ordered by next action time and stable ID. Claim a bounded batch with `SKIP LOCKED` or an equivalent atomic pattern. Enforce one active submission claim per Social Account while allowing unrelated accounts to proceed. Provider processing and delayed reconciliation release that submission slot.
- Parse publication configuration once at worker startup. Validate finite positive operation deadlines, heartbeat and lease relationships, batch and concurrency caps, backoff bounds, processing limits, provider API versions, and per-execution provider-call budgets. Invalid values fail startup.
- Persist a durable checkpoint before every provider call whose result is needed for recovery. The checkpoint records the normalized operation kind and provider identifiers. Bearer-like state such as resumable upload URLs is encrypted and never included in product snapshots, logs, analytics, or ordinary operator output.
- Before the final public-post creation call, persist `submission_started` with the provider operation identity and a stable Narriflow idempotency key. Adapters pass that key where the provider supports it. A timeout after this point is unknown until reconciliation proves accepted or failed.
- Normalize provider results to accepted, pending, failed, or unknown. Accepted includes a durable receipt and optional external URL. Pending includes an exact operation identity and next provider check. Failed includes a stable code and safe-retry or permanent disposition. Unknown means the provider may have accepted the operation and exact evidence is not yet available.
- Provider error classification uses response status, documented provider code, operation phase, and whether bytes or a submission request may have been accepted. Raw message text is diagnostic detail and never decides retry safety.
- Safe automatic retry is limited to definitive pre-submission failures and documented idempotent operations. It uses exponential backoff with jitter, honors `Retry-After`, has configured attempt and elapsed-time caps, and creates a new Social Publication Attempt only after the prior attempt is known not to have published.
- Pending provider work stores its next check and releases the worker. Reconciliation uses provider guidance and slows over time within a provider-specific bounded deadline. It never holds a worker lease while waiting minutes or hours for moderation.
- Unknown work first enters Reconciling when the adapter has exact or bounded recovery evidence. It becomes Needs attention when exact reconciliation is unavailable, credentials prevent it, the operation evidence expires, or the bounded reconciliation deadline ends without proof.
- YouTube persists the resumable upload session before sending video bytes. A replacement claim probes that session, resumes missing bytes, or receives the same completed video response. The returned video ID becomes the Provider Receipt, and processing status may be checked separately without re-uploading.
- Instagram persists the media container ID before `media_publish`. Container states distinguish upload readiness, processing, publication, expiry, and failure. A `PUBLISHED` container is accepted even if the lost publish response did not provide a media permalink; later receipt enrichment may add the media ID and URL.
- TikTok persists `publish_id` before upload and treats moderation as pending. Status fetches or verified content-posting webhooks settle the same attempt. A polling timeout remains pending or reconciling and never starts another direct post.
- LinkedIn persists the video URN and finalized upload state before Post creation. After a lost create response, the adapter uses the author finder and exact video URN within the bounded attempt window only when the account has the required read permission. Without that permission or an exact match, the outcome becomes unknown rather than failed.
- X persists the media ID and media key before Post creation. After a lost create response, the adapter may inspect the authorized user's recent Posts and match the exact attached media key within the bounded attempt window. Zero exact matches remain reconciling or unknown; more than one match requires attention.
- Replace the legacy publication webhook response contract directly. Requests carry a stable attempt idempotency key and signature. The receiver must return a durable receipt with accepted, pending, or failed, and pending must provide a signed or authenticated reconciliation contract. A bare 2xx without a receipt is unknown, not accepted. Do not retain the old success parser beside the new contract.
- The adapter capability contract declares supported recovery strength, asynchronous processing, idempotency support, required scopes, provider API version, and bounded operation limits. Product policy reacts to these facts; callers never branch on platform names.
- Social Post product states are Draft, Preparing video, Scheduled, Publishing, Processing on provider, Reconciling, Posted, Failed, Needs attention, and Cancelled. Safe automatic retry may project Scheduled with `nextAttemptAt` and retry context rather than add a separate durable status.
- Posted means provider-confirmed or manually confirmed. Failed means definitive non-publication. Needs attention means publication is possible but unproved. These meanings are invariant across the Publish view, Calendar, API, MCP, analytics, and operator tooling.
- Cancellation is compare-and-set against Draft, Preparing video, or Scheduled and must win before an attempt records submission start. After submission starts, the product cannot promise provider cancellation. The UI removes Cancel and explains the active state.
- Recheck acts only on the existing attempt and provider operation. It cannot create a new attempt. Confirm published requires `publishing.manage`, records the actor, reason, evidence kind, optional platform URL or ID, and whether the adapter validated ownership. Unvalidated confirmation is labeled manual and does not fabricate provider metrics.
- Publish again is available only from Needs attention, requires `publishing.manage`, shows platform-specific duplicate-risk copy, requires an explicit acknowledgement and bounded reason, and creates a new attempt linked to the uncertain one. It never rewrites the old attempt as failed.
- Account revocation blocks new preparation and submission immediately. An already submitted attempt may reconcile only while valid credentials remain. If revocation removes the evidence needed to reconcile, the attempt becomes Needs attention. The module never continues publishing under a disconnected account.
- Workspace restriction blocks new provider submissions and automatic retries. Attempts already accepted by a provider may continue read-only reconciliation and settlement so the product does not lose external truth.
- Commit the Provider Receipt, terminal attempt state, Social Post projection, and analytics intent in one transaction. Delivery of analytics or other downstream effects is replayable from durable intent. A downstream failure cannot move Posted back to Failed.
- Terminal settlement and receipt enrichment are idempotent. Replaying an accepted receipt returns the existing result. A conflicting provider post ID for the same attempt becomes an operator-attention condition and never overwrites earlier evidence.
- Keep external URLs optional. A provider-confirmed post without a retrievable permalink is still Posted and explains that the link is unavailable. Later enrichment may add the URL without changing publication truth.
- Provider preparation artifacts and uploads are cleaned up only when the adapter documents the deletion as safe and the attempt is definitively non-published. Unknown and accepted outcomes are never remotely deleted by automated cleanup. Cleanup failure is diagnostic and does not change publication truth.
- Structured logs use the repository JSON convention and stable attempt, claim, Social Post, workspace, account, platform, phase, operation, outcome, disposition, retry, duration, and cleanup fields. They exclude access and refresh tokens, signed URLs, resumable session URLs, raw provider bodies, captions, provider secrets, and complete external account IDs.
- Metrics cover admission replay and conflict, preparation duration and failure, queue age, claims, lease takeover, stale settlement, heartbeats, provider operation class and latency, pending age, reconciliation result and age, retries, rate limits, accepted, failed, unknown, Needs attention, manual confirmation, duplicate-risk republish, settlement replay, and cleanup.
- Provide an identifier-safe inspect-and-reconcile command for one Social Post or attempt. It defaults to read-only, never prints credentials or raw provider state, and requires an explicit action for recheck. It cannot publish again; that remains an audited product intent.
- Apply the pre-production compatibility policy. Migrate terminal Social Posts and reset or explicitly mark local nonterminal fixtures during a drained-worker cutover. Do not add dual attempt protocols, legacy provider switches, fallback status parsers, shadow publication, or mixed old and new workers.

## Testing Decisions

- The approved Social Publication Attempt `execute` interface is the highest and primary behavior-test seam. Tests provide an owned attempt and abort signal, drive deterministic internal adapters, and assert returned outcome plus observable attempt, claim, Social Post, receipt, analytics intent, retry schedule, and diagnostics.
- Behavior tests assert product outcomes and durable facts, not private helper calls, Prisma calls, request ordering that is not part of a provider contract, JSON layout, or worker loop implementation. Superseded helper tests are deleted once the same behavior is covered through the attempt interface.
- A deterministic platform adapter implements accepted, pending, failed, and unknown outcomes; idempotent and non-idempotent submission; exact and unavailable reconciliation; rate limits; credential expiry; delayed responses; conflicting receipts; and cleanup. A manual clock controls leases, heartbeats, scheduling, backoff, and processing deadlines.
- Attempt-interface tests cover exact frozen inputs, ordinary success, accepted without URL, pending then success, pending then failure, unknown then recovered success, unknown to Needs attention, safe automatic retry, permanent failure, abort, ownership loss, stale settlement, account serialization, settlement replay, manual confirmation, and duplicate-risk republish.
- Failure injection runs before and after attempt creation, claim, frozen-state load, credential load, media access, every provider preparation checkpoint, each upload segment, submission-start persistence, provider submission, receipt persistence, Social Post projection, analytics intent, retry scheduling, claim release, and cleanup.
- Crash-window tests prove that a process loss after provider acceptance but before database settlement results in reconciliation of the same provider operation. They also prove that a crash before submission may resume safely and that a stale claim cannot settle after takeover.
- Database contract tests use the repository's disposable PostgreSQL pattern. They prove schedule idempotency, immutable-input conflict, one active claim, one active account submission, keyset fairness beyond several batches, lease takeover, heartbeat, stale fencing, atomic terminal settlement, receipt uniqueness, exact export retention, retry lineage, and rollback at every transaction boundary.
- Concurrency tests cover two schedulers using one idempotency key, cancellation racing claim, two workers claiming the same due post, two posts for one account, unrelated accounts, claim expiry during upload, manual recheck racing background reconciliation, and manual republish racing late provider success.
- Media tests prove that scheduling freezes one completed Clip Export Variant and that later editor revisions, exports, ordinary render-cache changes, object grants, or account metadata cannot change the attempt bytes. Missing or deleted frozen media fails before provider submission.
- YouTube adapter contracts cover session initiation, encrypted session persistence, chunk resume, status probe after a lost upload response, repeated completed response, expired session, processing success and failure, quota, authentication, rate limits, and no second video insertion after uncertainty.
- Instagram adapter contracts cover container creation, processing, `FINISHED`, `PUBLISHED`, `ERROR`, `EXPIRED`, lost `media_publish` response, receipt enrichment, permission loss, publishing limits, and no second container publication after uncertainty.
- TikTok adapter contracts cover creator facts, init and `publish_id`, chunk upload, prolonged moderation, status and webhook settlement, provider failure reasons, rate limits, duplicate webhook delivery, polling timeout, and no second direct post for one attempt.
- LinkedIn adapter contracts cover upload initialization, multipart completion, video readiness, Post creation, `x-restli-id`, lost create response, exact author-finder match, missing read scope, zero and multiple matches, version headers, rate limits, and unknown classification.
- X adapter contracts cover media initialization, chunk resume, processing status, Post creation, lost create response, exact recent-timeline media-key match, zero and multiple matches, token scope, rate limits, and unknown classification.
- Publication webhook contracts cover signature verification, stable idempotency key, accepted receipt, pending plus reconciliation, definitive failure, duplicate request, lost response, conflicting receipt, invalid response, authentication failure, and the rule that bare 2xx is unknown.
- Provider contracts use pinned sanitized fixtures for the default suite and isolated opt-in sandbox accounts where provider programs permit automated tests. Tests verify current official contracts without operating on unrelated accounts or live customer content.
- Worker tests prove bounded concurrency, keyset fairness, account serialization, provider-loop isolation, lease heartbeats, pending release, due reconciliation, graceful shutdown, and that one slow or failing attempt does not block later accounts or ingest, Workflow Run, billing, notification, and retention loops.
- HTTP and MCP contract tests prove authentication, workspace isolation, strict idempotent scheduling input, typed state and action mappings, permission checks, retry guidance, cancellation races, recheck-only behavior, manual-confirm evidence, and duplicate-risk republish audit.
- React tests cover Preparing video, Scheduled, Publishing, Processing on provider, Reconciling, Posted, Failed, Needs attention, retry timing, reconnect guidance, stale polling, accessible announcements, focus movement, disabled cancellation, validated and manual confirmation, duplicate warning, and absence of raw enums or provider errors.

## Out of Scope

- Adding Facebook or another social platform.
- Assisted copy, generated hashtags, thumbnails, bulk scheduling, campaign operations, or Review approval gates. Their existing expansion specification should build on this lifecycle rather than enter it.
- Editing a frozen scheduled post in place. A content change cancels and reschedules before submission, or creates a new audited intent after submission.
- Deleting, editing, hiding, or moderating a post after the provider confirms publication.
- Building cross-platform exactly-once guarantees. External providers do not offer one shared transaction. This specification provides durable evidence, idempotency where available, reconciliation, and explicit uncertainty.
- Replacing Social OAuth account connection, token encryption, or provider app-review workflows except where additional read scopes are explicitly required for reconciliation.
- Redesigning engagement metrics collection, social analytics dashboards, Calendar layout, or the general Publish-page information architecture beyond the states and recovery actions required here.
- Generalizing Social Publication Attempt into Workflow Run, Campaign Operation, a repository-wide job framework, or a generic distributed transaction engine.
- Automatically deleting ambiguous provider media, containers, posts, or uploads.
- Preserving local-only in-flight rows from the obsolete pre-production publisher through a compatibility layer.
- Implementing the feature in this specification task. Each approved ticket is built separately.

## Further Notes

- The core guarantee is not "exactly once." No local transaction can atomically include five social providers and an arbitrary webhook receiver. The contract is one durable local attempt per provider operation, exact recovery where the provider exposes evidence, and an honest Needs attention state everywhere else.
- YouTube documents that a status probe against a resumable upload session returns the same completion response when the upload already finished. Persisting the session before bytes are sent makes lost-response recovery practical: https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol
- Meta's official Instagram Postman collection documents container states including `PUBLISHED` and recommends querying container status when `media_publish` does not return the media ID: https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api
- TikTok exposes status fetching and content-posting webhooks keyed by the durable `publish_id`; moderation may take hours, which is why provider processing must release the worker: https://developers.tiktok.com/docs/en/content-posting-api-reference-get-video-status
- LinkedIn returns the created Post ID in `x-restli-id`. Its author finder can match an exact video URN, but member and organization reads require separate restricted permissions. Missing read permission must therefore remain a product-level uncertainty: https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-03
- X exposes media upload status and user timelines with attached media-key expansion. These facts can reconcile a lost create response when access and an exact match are available; the create endpoint itself does not document a Narriflow-controlled idempotency key: https://docs.x.com/x-api/media/get-media-upload-status and https://docs.x.com/x-api/posts/timelines/integrate
- Existing Clip Exports are immutable delivery records for exact editor revisions and output configurations. They are the right media identity for publication; mutable ordinary render selection is not.
- The completed Workflow Run, Clip Render Attempt, Upload Session, and Workspace Billing work provide the local patterns for attempt fencing, deterministic adapters, bounded reconciliation, atomic durable transitions, direct pre-production cutover, and disposable PostgreSQL recovery drills.
- Implementation should follow the approved dependency-ordered local tickets. Each ticket starts in a fresh task, uses test-driven development, and finishes with Standards and Spec review plus uncached verification.
