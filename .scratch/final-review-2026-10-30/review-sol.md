### F1 · P0 · A delayed Clerk update restores a deleted account's API access

- **Location:** [packages/auth/src/identity.ts:143](/Users/murtaza/Documents/dev/narriflow/packages/auth/src/identity.ts:143), also the unconditional update at line 151 and conflict recovery at line 168. [apps/api/src/domains/platform/clerk/webhook.ts:65](/Users/murtaza/Documents/dev/narriflow/apps/api/src/domains/platform/clerk/webhook.ts:65) dispatches older signed user payloads without an ordering check.
- **Scenario:** Clerk delivers `user.deleted`, then a delayed or retried, previously unprocessed `user.updated` or `user.created` for the same Clerk ID. Deletion sets `User.deletedAt` and removes AuthIdentity rows, but retains memberships and API keys. The older update unconditionally writes `deletedAt: null`. An existing `nf_` credential then passes both API-key verification and live Workspace admission again, although the identity remains deleted in Clerk. No new browser session is needed.
- **Evidence:** `bun test /tmp/nf-sol-repro/auth-reorder.test.ts` exercises the actual identity sync, deletion, API-key authentication and Workspace admission implementations with an injected in-memory Prisma client. Admission refuses immediately after deletion, then succeeds after a payload with an older `updated_at`. Output: `{"deletedAt":null,"apiKeyStillValid":true,"restoredCapability":true,"directoryCalls":0}`. The implicated live gate is [workspace.service.ts:276](/Users/murtaza/Documents/dev/narriflow/packages/services/src/workspace.service.ts:276). Signature verification and delivery-ID deduplication do not establish ordering between different events.
- **Fix:** Make Clerk deletion terminal for that Clerk identity through a durable tombstone and conditional writes. An older create/update must not clear it, including through uniqueness-conflict recovery. Account for delete-before-first-provision ordering too. Revoke the user's API keys on deletion as defense in depth. Add regression coverage for reordered and concurrent events, verifying REST and MCP credentials stay refused.

### F2 · P2 · Failed Workspace recovery reopens the rejected cached selection

- **Location:** [apps/web/app/_components/workspace-query-gate.tsx:162](/Users/murtaza/Documents/dev/narriflow/apps/web/app/_components/workspace-query-gate.tsx:162) and the error condition at line 207.

- **Fix:** After a selection refusal, adopt only a successful fresh bootstrap result. Keep the shell closed on refresh failure and show GateFailure even when stale data exists. Preserve a working retry path and test this cached-data error case.

## Resolution (Claude)

### F1 (P0) fixed: Clerk deletion is terminal

- **Tombstone.** New table `ClerkDeletedIdentity(clerkId PK, deletedAt)`, migration `20261030150000_clerk_deleted_identity`. It is additive and never touched by the code that runs today, so it can be applied before the new code deploys. It backfills a tombstone for every already soft-deleted `User`. The Clerk id is the key because Clerk never reuses ids, so no timestamp comparison is needed (`updated_at` is deliberately not trusted).
- **Writes.** `markUserDeletedByClerkId` and the `syncClerkUserPayload` write (user upsert plus identities) each run in one transaction that first takes `pg_advisory_xact_lock` on the Clerk id. The sync checks the tombstone under that lock and throws `ClerkIdentityDeletedError`, also when the row is already soft-deleted. `deletedAt: null` is no longer written at all. This closes older update, older create, delete-before-first-provision and concurrent interleavings. The old same-Clerk-id race recovery is gone, because the lock serializes it. Email-conflict recovery stays.
- **Deletion side effects (same transaction).**
  - It tombstones the identity.
  - It removes the user's identities.
  - It revokes API keys where the user is the owner or the creator.
  - It revokes standing grants the user made, with an audit event.
  - MCP continuations are stateless, signed and revalidated against the credential, so revoking the key ends them. `McpTask.expiresAt` is DB-immutable, and tasks are only reachable through admission, which now refuses their owner.
- **Admission.** `workspaceService.authenticateApiKey` returns null for a deleted key owner or deleted creator. REST and the MCP verifier share it, and `requireActor` already refuses deleted users.
- **Webhook.** The runtime acknowledges a stale create/update for a tombstoned identity (it logs `clerk_stale_user_event_ignored`) instead of retrying forever.
- **Tests.**
  - `apps/api/src/domains/platform/clerk/clerk-deletion.db.test.ts` is added to `test:authenticated-request-policy:db` (17/17 pass via db-gate.sh). It covers reordered events, delete-before-provision, and concurrent delete/update/create in random interleavings, plus REST key auth, the MCP verifier and `requireActor` refusing, and key restoration still being refused.
  - Unit tests added to `packages/auth/test-fixtures/personal-workspace-auth.ts` (tombstone and soft-deleted-row refusal, deletion side-effect order).
  - `test:integration-api:db` is unchanged and still passes (7/7).

### F3 (P2) fixed: Clerk email relay is retry-safe

- **Delivery claim.** `claimWebhookDelivery` replaces the read-then-act check. It atomically creates the `WebhookDeliveryLog` row as `processing`, and only one of several overlapping deliveries gets it.
  - `success` returns `replay` (200).
  - A fresh `processing` row returns `in_progress` (409), so Clerk redelivers.
  - `failed` rows and `processing` rows older than the 2-minute lease are taken over.
  - No transaction spans the network send.
- **Idempotency key.** The verified Svix id now reaches the relay, which sends `clerk-email/<svixId>` as the Resend idempotency key. A retry after "sent, but log write failed" reuses the same key.
- **Tests.** `webhook.test.ts` covers overlapping deliveries (one relay, second gets 409) and send-ok/log-fail followed by a retry (same delivery id). `runtime.test.ts` asserts the key is `clerk-email/msg_abc` on both attempts. `packages/email/src/mailer.test.ts` asserts the key reaches Resend. The DB test covers claim exclusivity, replay and lease takeover.
