# MCP implementation spec review

Reviewed the working tree on `dev` against baseline `6a31c20f75be0a67daf86e3046bcb5e47598ff44` and the approved [spec](spec.md), including new untracked implementation files. This review checks the requested behavior and its acceptance boundaries; it does not establish live client launch readiness.

## Findings and resolutions

| Priority | Spec requirement and discovered gap | Resolution in the current working tree |
| --- | --- | --- |
| P1 | Cooperative Tasks cancellation must affect its referenced work. Export cancellation previously depended on an attached rendering run and could cancel every export sharing that project run. | `packages/services/src/mcp-task-runtime.ts` now delegates export cancellation by export ID to `clipExportService.cancelQueuedOperation`. That service locks pending render children, cancels only the selected export's pending work, and leaves claimed work and shared runs authoritative. Root owns the final disposable database race verification. |
| P1 | Exact publication confirmation must show every consequential accepted field. The original broad scheduling input also admitted thumbnail, assisted-copy selection, immediate scheduling and review override fields that the cards did not show. | `packages/validators/src/mcp.ts` now admits only the explicitly supported publication intent and rejects the hidden fields. The App and web page display all remaining consequential fields; the web page also resolves the current destination name/handle and workspace name. The authoritative scheduling review gate remains in force. |
| P2 | Export progress must refer to the export. The progress card refreshed only project generation and ignored its export snapshot. | `packages/mcp-core/src/mcp-apps/v2/progress.ts` selects `narriflow_get_clip_export` with exact workspace/project/clip/export identifiers for export work and `narriflow_get_project` for ingest/generation. The view renders export status/progress first. Three deterministic progress tests cover ordinary results and flat Tasks metadata. |
| P2 | Apps and Tasks must compose when both extensions are negotiated. Replacing an accepted tool result with a flat task handle discarded the App's operation identifiers. | `packages/mcp-core/src/mcp-tasks.ts` retains only the validated `narriflow/operation` projection on the task handle. Upload grants and other private metadata are not copied. Root added wire coverage; the App's exact export/project routing is independently tested. |
| P2 | Task retention must not shorten domain replay lifetime. Registering an accepted operation after its retained task expired returned an error until cleanup deleted that row. | The registry distinguishes expired registration and the dispatcher returns the ordinary accepted result for that case. Expired task get/update/cancel remain unavailable. Root owns the registry/wire tests. |
| P2 | The picker must let the assistant continue the clip workflow. Its accepted project/job identifiers were only in private transfer metadata and never reached conversation context. | `packages/mcp-core/src/mcp-apps/v2/upload-progress.ts` projects only durable workspace/project/ingest identifiers, status-tool guidance and an ordinary Narriflow link. The picker sends this projection through capability-gated standard bridge context/message methods. Unsupported or disconnected hosts receive visible status guidance without treating an accepted upload as failed. Tests prove private grants/storage fields are excluded. |
| P2 | Exact-post decisions must remain accurate after success and lost responses. The card re-enabled both decisions after scheduling and displayed an incorrect failure for a normal decline; after a lost scheduling response it could claim that a later decline meant no post existed. | `packages/mcp-core/src/mcp-apps/v2/publication-decision.ts` makes scheduling and decline terminal. An attempted schedule with an unavailable response remains uncertain, prohibits decline, and permits retry of the same immutable intent/key with its retained confirmation receipt. Tests cover concurrent decisions, terminal outcomes and lost-response recovery. |
| P2 | The ten-minute confirmation expiry must hold at new domain acceptance. The web action checked expiry before awaiting fresh credential, limiter and database admission, whereas the MCP tool also checked at acceptance. | `apps/web/app/(app)/integrations/mcp/confirm/actions.ts` verifies signed preparation again inside `beforeAccept`; an already accepted publication replay remains owned by the domain service. |

No further confirmed implementation gap remained from this spec review after those changes. Repository-wide integration, database checks and the external release gates below still determine readiness.

## Requirement checks

| Area | Current implementation and limits |
| --- | --- |
| Authentication and transport | Online Clerk response validation includes canonical MCP audience, expiry/revocation and application scopes. HTTP and stdio share current admission; stdio authenticates every inbound request. Exact browser origins, accepted-origin-only CORS, streamed 1 MiB bounds, private results and retryable upstream failures are present. Modern/older exchanges and scope challenges have deterministic wire coverage. |
| Retry safety and outage policy | Domain-owned fingerprints and transactional replay identities cover intake, generation, export, RSS and publication work. Request budgets remain enforced for every transfer action; unavailable limiter state pauses new writes while preserving accepted upload transfers and accepted replays. Signed web uploads bind caller/workspace/key/frozen settings and resume only owned accepted sessions after handoff expiry. |
| Public tool contracts | Strict validators and explicit project/clip/export/account/publication projections replace internal snapshots. Discovery uses `workspaceId`; mutations select it explicitly. Clip pagination is 20 by default and capped at 50; excerpt queries are opt-in. The public catalog has 23 tools, with App-only transfer/decision tools identified separately. |
| Clip workflow | Link intake commits generation defaults atomically; generation/export/publication use existing quota, revision and review services. Uploads reuse Upload Sessions for exact-object verification, multipart resume and atomic ingest handoff. The local helper sends credentials only to Narriflow and bytes directly to storage. |
| Apps | Four versioned HTML views use the standard bundled bridge, capability enforcement and explicit application/storage/media CSP origins. Templates contain no caller data. Private grants and preview URLs remain in `_meta`; accepted upload conversation context is separately projected. Embedding Studio and host attachment adapters remain outside this implementation unless their host contract is tested. |
| Tasks | Negotiated modern dispatch supports get/update/cancel with durable ownership, seven-day retention, five-second suggested polling and immutable terminal snapshots. Existing domain workers execute work. Ordinary durable-ID results remain available without Tasks and after task retention expires. Cancellation is cooperative and must still pass the final affected database gates. |
| Documentation and delivery | The sourced audit, dependent tickets, integration guide and launch acceptance runbook exist. The integration UI reports verified discovery/configuration facts rather than an unconditional Ready status. Deterministic MCP tests and disposable-schema acceptance are wired into CI. Root owns final repository-wide verification and evidence updates. |
