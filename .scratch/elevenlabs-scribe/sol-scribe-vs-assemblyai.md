# AssemblyAI versus ElevenLabs Scribe v2 for Narriflow

Research date: **October 29, 2026**. Research only. No repository files changed, no paid jobs submitted, no credentials read. Sources are current vendor documentation, vendor-authored releases and SDKs, Narriflow source, and Kalakar source fetched from its default `staging` branch. Undated living documentation below was retrieved on this date; an access date is not a publication date. Price calculations are estimates, not account-specific quotes.

## Verdict

**Route provisionally; do not make a global switch yet.** Explicit Urdu should be the first Scribe v2 route, subject to checking the existing output against the audio for substitutions and hallucinations. Keep the remaining routes on the current AssemblyAI model chain until Claude's scored, approximately 14-language FLEURS results arrive. If Scribe wins or matches the important languages and passes long-form speaker/timing checks, **switch to Scribe as the default and remove unnecessary AssemblyAI routes**. A permanent two-provider system needs measured benefits that pay for its operational cost.

The owner-provided 16-minute Urdu result is compelling operational evidence: Scribe v2 with Urdu selected produced 3,483 words and no gaps over three seconds; explicit-Urdu Universal-2 produced 3,272 words and ten gaps totaling 48 seconds; auto-detected U3.5 Pro omitted 226 seconds. Those are coverage observations, **not scored recognition accuracy**. More words and fewer gaps can also include hallucinations. There is no reason to rerun paid jobs during this research. The earlier [local defect review](/tmp/urdu-debug/sol/review.md) also establishes that recognition omissions and bad word alignment are separate problems.

Switching is technically feasible. Narriflow already has a provider-independent word/utterance schema and exports its own subtitles. The work is a moderate integration, not a caption-engine rewrite. The difficult part is preserving durable Workflow Attempt ownership while replacing AssemblyAI's submit/poll protocol with Scribe's async result delivery. Native versus Roman captions should be a separate text transformation after recognition; choosing Roman Urdu should never silently change recognition to Hindi or auto-detection.

Scribe does **not** require a new synchronous multi-minute request for every Narriflow video. Use its async mode. Conversely, the existence of Get transcript does **not** establish safe drop-in polling of the accepted `request_id`: the request ID and stored transcription ID are different documented fields. Before implementation, resolve not-ready GET responses, async-ID availability, result storage lifetime and failed-job recovery from the current API/support contract. Those are non-paid protocol checks, not reasons to rerun recognition benchmarks.

## Integration assessment against Narriflow

### What already works as a provider seam

[packages/validators/src/transcript.ts](/Users/murtaza/Documents/dev/narriflow/packages/validators/src/transcript.ts) already defines `TranscriptWord`, `TranscriptUtterance` and `TranscriptSnapshot`. Words have text, seconds and nullable confidence; utterances have speaker index/label, start/end, text and words. Snapshot provider/model/job IDs and language metadata are nullable strings/numbers. Prisma's `Transcript.provider`, `providerModel` and `providerJobId` are strings, not an AssemblyAI enum. **A provider switch alone does not inherently require a database migration.**

[transcript.service.ts](/Users/murtaza/Documents/dev/narriflow/packages/services/src/transcript.service.ts) is partly provider-specific: `NormalizedTranscript.provider` is literally `"assemblyai"`, and `normalizeAssemblyAiTranscript` assumes AssemblyAI's diarized utterance array. It converts milliseconds to seconds, maps speaker labels to stable integers, requires timed words and speaker labels, handles permitted empty transcripts, and calls `splitUtterancesIntoSentences`. The rest of that module builds snapshots and TXT/SRT/VTT exports from canonical utterances.

A clean Scribe normalizer should:

1. Filter `spacing` and `audio_event` tokens without discarding punctuation attached to actual words. Check finite, nonnegative start/end times and preserve real gaps/overlaps. A missing timestamp must not silently become zero.
2. Group consecutive words by speaker ID into turns; preserve cross-speaker overlap, map IDs to canonical speaker indexes, and run the **same** sentence splitter used today. Define missing-speaker behavior explicitly rather than treating unknown identity as a detected speaker.
3. Keep `logprob` in raw JSON. Canonical confidence can stay null. Exponentiating finite logprob gives a probability-like value, but not calibrated AssemblyAI confidence; do not compare thresholds across providers without validation.
4. Map `language_probability` to detected language confidence and three-letter language codes to product codes. Record the requested model because Scribe's result schema does not guarantee an AssemblyAI-style `speech_model_used` field. Read `audio_duration_secs` if present, with source-probe duration as the trusted source duration; never derive billing from the final word's end.
5. Keep current `allowEmpty` behavior for music/no speech, supplied captions and declined captions. Feed downstream captioning, clip detection, speaker-aware layouts, dubbing and search exactly the same canonical shapes.

This does not need a universal provider SDK interface. One small transcription request/result contract, one Scribe adapter, the existing AssemblyAI adapter only while it serves a measured route, and one pure `selectTranscriptionRoute(languageCode)` function are enough. Domain logic belongs in services; runtime wiring can use `<concept>-runtime.ts`. Neither provider SDK nor business logic belongs in web.

### Async integration is the main engineering decision

The simplest production fit is Scribe async submit, signed callback, and the **existing** Waiting Workflow Run lifecycle. The callback lives on API origin A, never in `apps/web`. It verifies the raw-body HMAC or configured OAuth, validates payload, and calls services. Route admission must declare `provider_signature`; business logic and settlement stay in services. [API architecture ADR](/Users/murtaza/Documents/dev/narriflow/docs/adr/0017-standalone-api.md), [workflow ADR](/Users/murtaza/Documents/dev/narriflow/docs/adr/0001-workflow-run-lifecycle.md), [Scribe webhook protocol](https://elevenlabs.io/docs/eleven-api/guides/how-to/speech-to-text/batch/webhooks).

Use callback metadata for project, Workflow Run and Workflow Attempt IDs. Persist the accepted provider and result correlation before releasing the attempt. Scribe distinguishes `request_id` from optional `transcription_id`; decide deliberately which goes into `providerJobId` and persist any other required recovery reference. Existing string columns can cover a basic swap, but a durable additional request-reference field may justify one small migration. Do not hide structured IDs in ad hoc encoded strings. A callback can arrive before `waitForProvider` commits, so settlement must use the current attempt fence or a small durable receipt, with retries enabled. No generic new event bus is necessary.

The waiting loop should remain a timeout/recovery backstop. It may retrieve a finished stored transcript by transcription ID where supported; it must not interpret a not-ready/404 response as proof of permanent job failure without a documented contract. With ZRM there is no stored result, so delivery guarantees and enabled retries become more important. This is the one area where clarification from ElevenLabs could change the integration estimate.

A synchronous Scribe call can make a small prototype easy, but replacing `submit` with a long `await convert()` inside today's 30-second submission code is not an acceptable production swap. It holds a worker, ties result survival to a socket/process, needs different timeouts, and may produce duplicate charges on retry after lost responses. Railway does not require uploading a full video when provider-side URL fetch works. If upload is necessary, reuse Worker Process Module scratch lifetimes and stream the small extracted audio; Kalakar's whole-file Buffer/Blob is a poor template for Narriflow's multi-hour sources.

## Routing and native/Roman captions

### Minimal route policy

Prefer **one default provider plus a small, evidence-backed override map**. Exact user language must be passed through to recognition even when the chosen provider stays the same. That alone fixes the observed Urdu-to-Hindi auto-routing problem, though it does not repair U2's missing speech. A provider picker or a 100-row mutable rules database would add little value.

| User's source language | Initial policy before scored results | What would change it |
| --- | --- | --- |
| `ur` | Provisional Scribe `scribe_v2`, explicit Urdu hint. Validate the existing long sample against audio; retain native text. | Claude's scored Urdu/CER result and long-form checks can confirm or reject it. |
| `pa`, `ps`, `sd` | Preserve current explicit-language U2 path until measured. Scribe is a serious candidate, especially Punjabi, based on vendor bands rather than proven Narriflow accuracy. | Move only languages with a meaningful measured win, including correct script/dialect. |
| `bn`, `ta`, `te`, `mr`, `gu`, `fa` | Benchmark-priority candidates; do not declare Scribe the winner solely from its much better advertised bands. | Add only winning routes; collapse to Scribe default if broad results support it. |
| `hi`, `ar`, `en` and other current U3.5 languages | Keep current explicit-language chain pending scored results. | Scribe must match accuracy and speaker/timestamp quality, or win enough to justify switching. |
| `skr`, `ks`, `bal` | No documented supported route in these two vendors. Do not silently alias. | A verified provider/dialect becomes a deliberate product addition. |
| `auto` | Preserve a known default provider; present detected language and permit correction. Do not feed an unverified detected Hindi label into every recovery attempt. | Make Scribe the auto default if controlled detection/script tests show it is safer. |

This table is a rollout recommendation, not a benchmark result. It is also not a recommendation for permanent dual transcription. Calling both providers on every file doubles provider work and creates arbitration problems. Try one selected route, retain typed failures, and offer a deliberate retry/correction when evidence says the transcript is bad. A measured current-provider recovery path is possible later; an automatic fallback to obsolete code conflicts with AGENTS.md.

Store the actual selected provider/model on the pending attempt before the external call/wait, and complete with actual returned model metadata where available. Do not recompute the route at every poll or callback: a deployment can change the map while earlier work is still pending. Requested source language, detected language and output script are different facts.

An exact routing map also has limits. It does not make `language_code` a hard Scribe restriction, solve code-switching by itself, distinguish every Punjabi variety, or make a one-sentence FLEURS winner the best provider for a two-hour interview. Add a route when it has both short-form evidence and representative long-form evidence. When the winner becomes broadly uniform, deleting the router overrides is the simpler design.

### What Kalakar actually does

The current source is more specific than "Kalakar picks an exact language and Scribe returns Roman text":

- Its main [transcription processor](https://github.com/kalakar-es/kalakar/blob/staging/apps/video-worker/src/processor/transcription.ts) explicitly selects `scribe_v2`. Sarvam is selected by a `useSarvam` preference plus the supported-language set; it can fall back to ElevenLabs on error. This is not a scored language-to-provider map.
- Its [ElevenLabs adapter](https://github.com/kalakar-es/kalakar/blob/staging/apps/video-worker/src/services/elevenlabs.ts) only forwards certain hints. Urdu is pinned **only for Native script**; Roman Urdu passes null. Several other language/script combinations also auto-detect. That behavior should not be copied into Narriflow's exact-language promise.
- Its [segment service](https://github.com/kalakar-es/kalakar/blob/staging/apps/video-worker/src/services/segment.ts) uses overlapping chunks, adds segment offsets to word times, and filters overlap words. The processor uses 30/60-second chunks for several Indic languages and Urdu, versus generally 120 seconds for others. These are application choices, not Scribe's batch limits. Segmented speaker IDs would also need global reconciliation if diarization were enabled.
- Its current [Roman/native processor](https://github.com/kalakar-es/kalakar/blob/staging/apps/video-worker/src/processor/native-script.ts) calls [romanize-pairs.ts](https://github.com/kalakar-es/kalakar/blob/staging/apps/video-worker/src/services/romanize-pairs.ts), whose default model is `gpt-5.1`, overridable by `ROMANIZE_PAIRS_MODEL`. It asks for one `[original, other-script]` pair per source word, structured JSON, no additions/skips and a single output word. It batches 120 words with six requests in parallel, matches the returned originals back, retries unmatched words once, and keeps original text when conversion fails. Arabic-script inputs preserve ordered occurrences rather than deduplicating ambiguous homographs.
- It preserves timing by copying each original word object and replacing only `text`, optionally attaching `nativeText`. There is no new ASR or forced alignment for the normal Scribe Romanization path. Its current implementation can still leave mixed script after failed conversions, with telemetry rather than a hard product failure.
- For Sarvam, it gets text first, calls ElevenLabs forced alignment, filters whitespace/zero-length entries, and attaches native spellings. It warns when a word lasts more than two seconds because missing text can make the aligner stretch neighbors. The current processor's Sarvam comments and implementation disagree about Batch-versus-REST order; the actual code tries REST-chunked first, Batch second. Copy the validated idea, not those comments or all the fallback machinery.

### Recommended script design

1. Capture source language and **caption script** independently: native or Roman for languages where the product supports it. Recognition always uses the source-language choice. Romanization is transliteration, not English translation.
2. Keep native recognition words/times as the canonical source and raw vendor JSON for diagnosis. If Roman captions are requested, generate one display spelling per canonical word, retaining the original word identity, timing and speaker. Persist optional per-word Roman text and the selected output script so toggling does not repeat ASR or discard the native source. Update the current schema once; no dual-read legacy transcript format is needed.
3. Validate count, order and copied source text independently of the model's JSON schema. A schema saying "array of pairs" does not prove one entry per source word. Preserve English insertions deliberately. For ambiguous Arabic-script words use neighboring context; blind unique-word caching loses pronunciation/context distinctions.
4. Recompute utterance display text from selected word spellings, and let the existing composition cue policy handle wrapping. Never replace timed words with free-form translated/rewritten text. If a transformation merges/splits lexical words, either preserve a timed source-word span explicitly or treat that as a separate alignment feature.
5. A failed Roman conversion should produce a typed, visible retryable state or an explicitly disclosed partial result. Silently shipping a mixture under a "Roman Urdu" choice is unsurprising only to the implementation, not the user. Keep native captions available.

This feature costs LLM latency/money and introduces text-quality validation. It does not require an STT provider switch, and Scribe's `transcript_edit` is not a documented substitute for per-word transliteration with unchanged timings. Sarvam plus alignment should remain a separate, benchmark-justified option; adding it merely because Kalakar has it expands the scope from one recognizer to text recognition, alignment and speaker reconciliation.
