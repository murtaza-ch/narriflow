# Deepen Upload Session intake and reconciliation

**Status:** ready-for-agent

## Problem Statement

Creators need local video and audio uploads to survive slow networks, refreshes, retries, expired grants, and ambiguous storage responses without creating duplicate projects or asking them to guess whether an upload worked. Today Project creation, provider multipart state, Upload Session persistence, Content Pack creation, and Ingest Job admission cross several non-atomic steps. A fresh request has no durable client idempotency key. The browser and request validators treat the provider upload ID as a UUID even though storage providers define it as an opaque string. Finalization completes the provider upload before recording the intent needed to recover it. When that response or the following database write is lost, the system can identify `reconciliation_required` but cannot converge it. Expired and abandoned multipart uploads are marked locally without prompt provider cleanup.

The interface also exposes details callers should not own. The browser supplies the part count, provider upload ID, storage key, and complete set of signed part URLs. Part sizing is duplicated in browser code, all files use multipart transfer, and a normal small upload pays for multipart initiation, several part writes, and completion. The current one-hour URL set can expire during a long upload, while returning hundreds of bearer URLs makes the first response larger than necessary. Existing tests prove pure classifiers and browser parsers, but they do not drive start, resume, finalize, compensation, reconciliation, and ingest handoff through one domain interface with injected failures.

## Solution

Introduce one deep, workspace-owned Upload Session module for local-file intake. Its public interface owns idempotent admission, transfer planning, grant refresh, resume, finalization intent, compensation, reconciliation, expiry, and exactly-once handoff to an Ingest Job. The browser receives only a Narriflow session ID, a server-planned transfer description, short-lived upload grants, progress facts, and typed outcomes. Provider upload IDs and object keys stay private.

The module chooses one direct signed PUT for files up to the validated small-file threshold and multipart transfer for larger files. Multipart size, count, uniformity, and limits come from the server. The normal path avoids provider inventory calls. Resume and ambiguous completion use exact provider probes only when needed. Before any irreversible completion call, the module persists the validated part inventory and frozen generation settings. A completion response can then be retried or reconciled after the browser, web process, or worker disappears.

An Upload Session begins as a durable reservation without creating a visible Project. Once the object exists with the declared byte length, one transaction creates the Project, Content Pack, Ingest Job, and queued lifecycle event, then marks the Upload Session `queued_for_ingest`. Failed, discarded, and expired sessions compensate their private provider state and leave no empty Project. A bounded worker sweep converges sessions that requests cannot settle inline. The browser shows Pause during byte transfer, Verifying after the commit point, and Discard only while cancellation is still safe.

## User Stories

1. As a creator, I want one click to start one upload, so that a retried request cannot create duplicate projects or storage work.
2. As a creator, I want a lost start response to return the same Upload Session, so that I do not upload the same file twice.
3. As a creator, I want the same selected file to resume automatically, so that a refresh or temporary network failure does not waste completed transfer work.
4. As a creator, I want a completed upload to open the same project when I retry, so that an already successful transfer never starts again.
5. As a creator, I want small files to start quickly, so that short audio and video do not pay multipart setup latency.
6. As a creator, I want large files uploaded in parallel parts, so that transfer throughput remains high and only failed parts need another attempt.
7. As a creator, I want long uploads to refresh expiring grants automatically, so that an expired bearer URL does not force a restart.
8. As a creator, I want progress based on transferred bytes, so that the percentage, speed, and ETA remain truthful when the last part is smaller.
9. As a creator, I want resumed bytes included in progress, so that the meter starts from the work already stored.
10. As a creator, I want transient part failures retried with bounded backoff, so that a short network interruption does not fail the whole upload.
11. As a creator, I want Pause to mean pause, so that stopping browser transfers preserves a resumable session.
12. As a creator, I want Discard to remove unfinished provider state, so that abandoning a file does not leave billable parts behind.
13. As a creator, I want the interface to explain when discard is no longer safe, so that I do not think a committed upload can still be canceled.
14. As a creator, I want the Verifying stage to recover on its own, so that I never see a dead-end instruction to contact support for an ordinary ambiguous response.
15. As a creator, I want to leave the page while verification continues, so that a slow provider response does not trap me on the upload screen.
16. As a creator, I want a later visit with the same file to discover the final project, so that closing the page during verification is harmless.
17. As a creator, I want invalid or changed local resume data ignored safely, so that browser storage corruption cannot attach my file to another session.
18. As a creator, I want my title, brand snapshot, language, clip settings, and caption settings frozen when I submit, so that a retry produces the project I asked for.
19. As a creator, I want a settings mismatch on an idempotent retry rejected clearly, so that one token cannot silently change an in-flight upload.
20. As a creator, I want exact declared file size checked before ingest, so that a truncated or substituted object is not accepted as my source.
21. As a creator, I want unsupported type and size errors before transfer begins, so that I do not spend time uploading a file Narriflow will reject immediately.
22. As a creator, I want the current 5 GiB product limit preserved, so that this architecture change does not alter the upload contract.
23. As a workspace member, I want every upload command authorized against the current workspace and capability, so that another member cannot resume or discard my session by guessing an ID.
24. As a workspace owner, I want quota admission performed once for a fresh session and skipped for idempotent resume, so that retries are fast and do not produce inconsistent billing decisions.
25. As an operator, I want provider upload IDs treated as opaque private values, so that a provider format change cannot break browser parsing.
26. As an operator, I want storage keys derived by the module, so that callers cannot redirect uploads into another project or workspace prefix.
27. As an operator, I want the server to compute transfer kind, part size, and part count, so that every client obeys provider limits and uniform-part rules.
28. As an operator, I want short-lived grants issued in bounded windows, so that first response latency and bearer-token exposure stay small.
29. As an operator, I want signed URLs generated locally without a provider round trip, so that grant refresh is cheap.
30. As an operator, I want normal upload completion to avoid ListParts, so that provider calls and Class A operation cost stay bounded.
31. As an operator, I want resume to list provider parts only when the client has actually lost its inventory, so that recovery cost is paid only on recovery.
32. As an operator, I want all completion facts persisted before provider completion, so that a worker can finish the same intent after a crash.
33. As an operator, I want finalization idempotent across concurrent browser requests, so that only one Project, Content Pack, and Ingest Job can be created.
34. As an operator, I want a provider timeout classified as ambiguous rather than failed, so that a completed object is adopted instead of uploaded again.
35. As an operator, I want an exact missing-upload response distinguished from bucket, permission, and transient failures, so that recovery never guesses from a generic 404.
36. As an operator, I want an initiating session to adopt its exact-key provider upload after a lost bind response, so that the narrow start ambiguity also converges.
37. As an operator, I want extra unfinished uploads for the same session key aborted, so that a rare duplicate provider initiation does not accrue storage.
38. As an operator, I want every expired session actively compensated, so that the provider's seven-day lifecycle is a backstop rather than the primary cleanup path.
39. As an operator, I want compensation replayable, so that a failed abort or delete is retried without damaging referenced objects.
40. As an operator, I want reconciliation claimed with a lease, so that several workers can sweep safely without duplicating provider calls or ingest handoffs.
41. As an operator, I want reconciliation work bounded by batch size, concurrency, deadlines, and backoff, so that maintenance cannot overwhelm R2 or the database.
42. As an operator, I want a session that reached its finalization commit point to finish even when the browser disappears, so that user presence is not part of correctness.
43. As an operator, I want a suspended workspace to block new transfer work while preserving an already accepted finalization intent, so that storage does not become orphaned during an account-state change.

## Implementation Decisions

- Add Upload Session to the domain glossary as one durable, workspace-owned local-file intake from idempotent admission through transfer, finalization, compensation, reconciliation, and exactly-once Ingest Job handoff. It is not a Workflow Run or an Ingest Job.
- Record the ownership and state-machine decision in an ADR. Upload Session owns intake until `queued_for_ingest`; Ingest Job owns media probing and normalization after that point. Project remains the durable product aggregate created at handoff.
- The module interface exposes five user or operator intents: open or resume, issue upload grants, finalize, discard, and reconcile due sessions. A status read is the read form of open or resume, not a separate state-changing protocol. Hono and the worker call this interface and do not reproduce transition rules.
- The module accepts an authenticated actor and workspace context, a client-generated idempotency key, a local file declaration, a browser file fingerprint, a title, a selected brand, and the complete validated generation settings. Provider IDs, object keys, part counts, and expiry decisions are never caller inputs.
- The browser creates and stores the idempotency key before the first request. A unique workspace and idempotency-key constraint returns the original session on replay. Reuse with different immutable source or generation inputs returns a typed idempotency conflict.
- The browser resume record stores only its current version, client idempotency key, Narriflow session ID, exact file fingerprint, and safe display facts. It never stores provider IDs, object keys, signed URLs, or completion ETags. Pre-production cutover replaces the old record directly rather than adding a legacy reader.
- The durable Upload Session is independent of Project while transfer is incomplete. It stores a preallocated project ID, workspace and actor ownership, source declaration, frozen brand snapshot, frozen generation settings, transfer plan, provider binding, completion intent, verification facts, reconciliation schedule, and terminal outcome. Failed intake therefore leaves no empty Project row.
- The durable states are `initiating`, `uploading`, `finalizing`, `reconciling`, `compensating`, `queued_for_ingest`, `aborted`, `expired`, and `failed`. Legal transitions and compare-and-set guards live only in the module. `queued_for_ingest` is terminal for Upload Session even though the Ingest Job is just beginning.
- Fresh admission first writes the durable reservation and unique storage key, then starts provider state. After a successful provider call, it binds the opaque provider upload ID. If that bind is lost, reconciliation lists unfinished multipart uploads for the exact session key, adopts one, and aborts extras. Provider lifecycle cleanup remains defense in depth for the final unobservable crash gap.
- The transfer planner keeps the current 5 GiB product limit. Files at or below 100 MiB use one direct presigned PUT by default. Larger files use multipart transfer with a 16 MiB default part size, four concurrent browser writes, uniform non-final parts, and a computed count no greater than 10,000. All values come from validated immutable configuration.
- The multipart planner increases part size when needed to stay within provider limits. It never accepts a browser-supplied part count. Exact thresholds remain configuration values with strict minimums, maximums, and startup validation so a bad environment value fails before intake starts.
- Upload grants are bearer tokens. The module returns at most 16 part grants at once with a 15-minute default lifetime. It issues only grants valid for the current session state and requested in-range part numbers. The browser requests a fresh window before expiry and treats an opaque cross-origin 403 near expiry as a grant-refresh case.
- The normal multipart path does not call ListParts. The browser records ETags from successful writes in memory. A true resume calls provider inventory once, follows pagination, validates unique in-range parts, and returns completed part facts plus fresh grants for missing parts.
- Finalize first validates and durably stores the complete ordered ETag set for multipart, or the single-transfer completion intent for PUT. It also stores the frozen Content Pack and language inputs before any provider completion call. A worker can therefore replay the exact operation without browser state.
- A successful provider completion is followed by one exact HeadObject verification. The object byte length must equal the declared source size. Content type is normalized against the declared supported type. Size mismatch is permanent and moves to compensation rather than ingest.
- The module classifies provider outcomes by stable identifiers. A timeout, connection loss, or retryable provider response after completion begins is ambiguous and enters reconciliation. Exact NoSuchUpload triggers an object probe. Bucket absence, permission failure, invalid parts, and malformed provider inventories remain distinct typed outcomes.
- Reconciliation probes the cheapest decisive fact first. If the exact object exists and passes verification, it performs the ingest handoff. If the object is absent and a persisted multipart completion can still run, it retries completion with bounded backoff. If neither the object nor provider upload exists, it fails or compensates according to the persisted state.
- Reconciliation claims use an internal attempt ID and expiring lease. Every state write checks the claim. A stale worker may finish a provider call but cannot overwrite a newer settlement. The next claim uses exact object state to adopt or compensate that side effect.
- The worker maintenance loop claims a bounded batch, defaults to 25 sessions with concurrency four, and applies exponential backoff with jitter and per-operation deadlines. Request paths make at most one short inline reconciliation attempt, then return `reconciling` with retry guidance rather than holding an HTTP request open.
- The handoff transaction creates exactly one Project with its preallocated ID, one Content Pack from the frozen generation settings, one Upload Finalize Ingest Job linked uniquely to the session, the verified source reference and metadata, and the queued lifecycle outbox event. It marks the Upload Session `queued_for_ingest` in the same transaction.
- The upload-finalize worker consumes verified size and content type from the handoff and avoids a duplicate HeadObject on the normal path. It still probes the media through a fresh private download grant and remains responsible for authoritative duration, media validity, quota and per-upload duration policy, normalization, and later post-ingest Workflow Run admission.
- Open, grant, and finalize reauthorize the actor, workspace status, and `processing.consume` capability. Resume checks database state before quota, brand, or provider work. Once finalization intent is durably accepted, system reconciliation completes or compensates it even if the browser closes or the actor later loses a session.
- Pause aborts browser transfers only and leaves the Upload Session resumable. Discard is allowed only before finalization intent. It stops active browser work first, moves the session to `compensating`, aborts multipart state or deletes a session-unique single object, and finishes as `aborted`. Abort and delete are idempotent.
- Sessions expire after 24 hours without accepted activity and have a hard lifetime below R2's default seven-day incomplete-upload cleanup. Grant issuance renews idle expiry within that hard cap. The maintenance sweep compensates expired sessions promptly and verifies the bucket lifecycle rule as a deployment prerequisite.
- The browser adapter owns byte transport only. It slices server-planned parts, aggregates byte progress through upload progress events, runs bounded concurrency, retries transient failures three times with jitter, refreshes grants, and reports Pause, Resume, Verifying, and Discard intents to the module. React renders its snapshot and sends user intents.
- During `finalizing` or `reconciling`, the primary action becomes a non-destructive status check. The UI says that Narriflow is verifying the upload and that the user may leave. It never offers a fresh-upload fallback for the same session until the server proves the old provider state and exact object are both absent.
- Expected outcomes use stable typed codes and transport mappings. Reconciliation is a `202` outcome, not an error. Invalid input, expired session, idempotency conflict, quota refusal, authorization loss, permanent integrity failure, and transient unavailability remain distinguishable without comparing message text.
- Structured logs follow the repository JSON convention. They include Upload Session ID, workspace ID, state, transfer kind, declared byte class, part count, provider operation class, reconciliation attempt, disposition, duration, and cleanup result. They exclude signed URLs, storage credentials, provider upload IDs, raw ETags, generation settings, and full provider errors.
- Metrics count session admission, replay, resume, transfer kind, planned parts, signed grants, completion parts, provider operation classes, inline and worker reconciliation, compensation, terminal outcomes, declared abandoned bytes, time to first grant, upload throughput, finalize duration, and time spent reconciling.
- The pre-production compatibility policy applies. Replace the existing Upload Session schema, local resume version, Project-owned orchestration, and HTTP payloads in one migration and cutover. Do not add dual reads, dual writes, legacy status parsers, a shadow module, or a feature selector.

## Testing Decisions

- The Upload Session module interface is the highest and primary behavior-test seam. Tests call open or resume, grant, finalize, discard, and reconcile with deterministic adapters, then assert returned outcomes plus durable session, project, content, ingest, event, and provider facts.
- Public-interface tests assert observable state and side effects, not private helper order, Prisma calls, SDK commands, signed URL text, or React effect sequencing. The existing pure part normalization tests remain only where they define an independent provider contract. Helper tests that duplicate the new interface behavior are removed.
- A deterministic in-memory storage adapter covers single PUT, multipart creation, grant issuance, part inventory pagination, completion, exact object probes, abort, delete, ambiguous outcomes, and provider error classification. A recording diagnostic adapter verifies stable fields and secret exclusion.
- Database contract tests use the existing disposable PostgreSQL pattern. They prove workspace idempotency uniqueness, immutable-input conflicts, legal state transitions, concurrent finalize fencing, reconciliation lease takeover, stale-claim rejection, exactly-once Project, Content Pack, Ingest Job and event creation, terminal compensation, and replay after transaction failure.
- Failure injection runs before and after reservation, provider creation, provider binding, every grant, finalization-intent persistence, provider completion, object verification, handoff transaction, event dispatch, abort, delete, lease claim, lease expiry, and terminal settlement.
- Start recovery tests cover a lost initial response, a provider upload created but not bound, zero, one, and several exact-key unfinished uploads, adoption, duplicate abort, provider list failure, and lifecycle backstop diagnostics.
- Resume tests cover completed single PUT, partial multipart inventory, all parts present, paginated inventory, overwritten part numbers, malformed ETags, unknown provider upload, expired grants, client clock skew, corrupt browser storage, storage unavailable, and exact-file versus other-file selection.
- Finalization tests cover duplicate and concurrent requests, missing and extra parts, invalid ordering, provider timeout before and after object creation, embedded completion failure handled by the SDK, exact NoSuchUpload, object size mismatch, database failure after provider success, and successful recovery without another upload.
- Compensation tests cover pause without abort, discard during active writes, abort after in-flight writes settle, already missing provider state, single-object deletion, cleanup denial, replay, expiry, and the rule that finalizing sessions cannot be user-discarded.
- Cost and performance tests assert provider operation counts. Small normal uploads use one PutObject and one verification probe. Large normal uploads use one initiation, the planned part writes, one completion, and one verification probe with no ListParts. Resume and ambiguity fixtures document their extra calls.
- Browser-adapter tests use fake HTTP, upload transport, local storage, clock, and progress adapters. They prove byte-accurate progress, bounded concurrency, backoff and jitter, grant refresh, pause and resume, finalize polling, navigation on `queued_for_ingest`, safe unload, typed errors, and no provider detail in browser persistence.
- Hono contract tests prove authentication, rate limiting, strict request validation, status mappings, Retry-After guidance, workspace isolation, and translation-only behavior. They do not duplicate state-machine cases already proven at the module seam.
- Production R2 contract tests use an isolated random prefix and explicit cleanup. They cover signed single PUT with Content-Type, multipart uniformity, ETag exposure, ListParts pagination, completion, exact HeadObject, NoSuchUpload classification, abort, delete, expired-grant behavior under CORS, and exact-key unfinished-upload listing.
- Real-browser verification covers a small audio PUT, a forced multipart video, pause and exact-file resume, refreshed grants, a simulated lost finalize response, Verifying UX, completed-session replay, discard, and navigation into a queued project with the frozen generation settings.
- Performance verification records time to first grant, response bytes, browser peak memory, throughput, retries, finalize latency, worker reconciliation latency, and provider operation counts for representative small, medium, 1 GiB, and 5 GiB fixtures. The new path must not reduce steady-state multipart throughput beyond the agreed measurement tolerance.
- Final verification runs uncached focused suites, disposable PostgreSQL contracts, opt-in isolated R2 contracts, repository typecheck, lint, full tests, and the production build. The final review covers both repository standards and this specification.

## Out of Scope

- Changing the 5 GiB product upload limit, supported media types, monthly processing-minute policy, per-tier duration limits, or billing semantics.
- Moving media probing, duration authority, normalization, transcription, clip generation, or other post-ingest work into Upload Session.
- Generalizing Upload Session into the Workflow Run lifecycle or replacing Ingest Job claiming, retry, reaping, and worker ownership.
- Adding background browser uploads that continue after the tab closes, native file-handle persistence, service-worker transfer, mobile-native upload SDKs, or multi-device resume.
- Building a workspace upload-history product, batch local-file uploads, folder uploads, or more than one visible concurrent upload in the current page.
- Adding virus scanning, content moderation, DRM inspection, a new media codec policy, or client-side full-file hashing. Exact byte length, HTTPS, provider ETags, and ingest probing remain the current integrity contract.
- Changing Brand Profile behavior, Content Pack product settings, project retention policy, link and RSS intake, or the Clip Composition Plan.
- Preserving incomplete local Upload Sessions or browser resume records created by the old pre-production implementation.
- Shipping implementation in this design task. Each approved ticket is implemented separately.

## Further Notes

- Cloudflare documents single PUT as the lower-overhead choice below roughly 100 MB and multipart transfer for large, parallel, resumable uploads. Multipart parts must be uniform except for the last, each non-final part must be at least 5 MiB, and one upload may contain at most 10,000 parts. See [Cloudflare R2 upload guidance](https://developers.cloudflare.com/r2/objects/upload-objects/).
- R2 charges CreateMultipartUpload, UploadPart, ListParts, and CompleteMultipartUpload as Class A operations. AbortMultipartUpload and DeleteObject are free. The operation-count assertions in this spec are cost controls, not incidental test details. See [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/).
- R2 automatically aborts incomplete multipart uploads after seven days by default, and Cloudflare allows a custom lifecycle policy. Application compensation remains necessary because one day of abandoned multi-gigabyte parts is still avoidable storage and the provider lifecycle cannot create the missing Project or Ingest Job.
- Cloudflare notes that expired presigned URL errors omit CORS headers, so browser JavaScript may see an opaque failure. Proactive grant refresh and typed server status are more reliable than parsing the R2 error body. See [Cloudflare R2 CORS guidance](https://developers.cloudflare.com/r2/buckets/cors/).
- Amazon S3 documents completion as retryable and potentially ambiguous even around an initial successful HTTP response. The AWS SDK handles embedded errors, but the application must still reconcile timeouts and lost responses against exact object state. See [CompleteMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).
- Direct browser-to-R2 transfer remains the right cost and scale choice. Narriflow servers sign scoped requests and own state; they do not proxy multi-gigabyte media through the web process.
- The completed Workflow Run, Studio Editing Session, Clip Render Attempt, and Clip Composition Plan work establishes the pattern used here: one domain owner, one public test seam, deterministic internal adapters, typed degradation or recovery, and no competing legacy path after cutover.
