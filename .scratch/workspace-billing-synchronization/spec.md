# Deepen Workspace Billing synchronization

**Status:** ready-for-agent

## Problem Statement

Workspace owners need plan access, project retention, paid seats, Checkout, and the billing portal to agree even when Stripe retries deliveries, sends events out of order, responds after a timeout, or succeeds before Narriflow commits its database write. Today webhook handling, Checkout return confirmation, customer provisioning, seat updates, and the hourly seat sweep can all change billing-related state without one durable owner.

The webhook path does not record Stripe event IDs in a durable inbox. It treats second-resolution event creation time as an ordering key, so equal-second and delayed events can overwrite newer access decisions. The Checkout return path retrieves a subscription and writes the tier directly, then shows a success toast even though the authoritative webhook and later subscription changes may not have converged. An unknown configured price falls back to Free, which turns configuration drift or a new Stripe price into an access revocation. Provider timeouts can also become user-facing failures even when Stripe accepted the operation.

Customer and seat changes cross Stripe and Postgres in the request path. Concurrent first checkouts can create more than one Stripe customer. A seat increase can succeed at Stripe and then fail before the member change commits, while concurrent role changes can send stale quantities. Creating the first seat item can race and produce duplicate subscription items. The periodic sweep selects a fixed oldest batch rather than maintaining per-workspace due state, so a larger installation can starve workspaces after the first page. Existing tests cover the pure feature matrix, but none drive delivery, reconciliation, entitlement projection, retention, customer identity, and seat recovery through the public billing interface.

The current UI reflects the same split ownership. It can say "You're upgraded" before the plan is active, hides the distinction between payment trouble and synchronization delay, and uses foreground Stripe calls to decide whether a membership action succeeded. Owners and members need stable states and useful recovery actions, not raw provider errors or optimistic confirmation that later disappears.

## Solution

Introduce one deep, workspace-owned Workspace Billing module. It owns signed Stripe delivery acceptance, durable delivery idempotency, current-state reconciliation, subscription policy, Workspace entitlement and retention projection, customer identity, Checkout attempts, paid seat convergence, retry scheduling, repair state, and the read model shown in billing and member settings. Hono, React, the worker, Postgres, and Stripe remain adapters.

A valid Stripe delivery is durably accepted once and returns quickly. The delivery is a notification, not entitlement truth. A bounded worker claim retrieves current provider state and derives one reconciled outcome from the configured price catalog and subscription-status policy. The module applies the Workspace tier, access status, project-retention transition, billing snapshot, and audit transition in one database transaction. Duplicate and shuffled deliveries therefore converge to the same result. If Stripe is unavailable or returns an unmapped state, Narriflow keeps the last verified entitlement and records a retry or operator-attention state instead of guessing Free.

Checkout and customer provisioning become replayable operations. Free and pending-payment workspaces use Checkout for the first subscription. Existing paid workspaces use Stripe's hosted billing portal for plan, interval, payment-method, invoice, and cancellation changes, which prevents Narriflow from creating a second subscription during an upgrade. A Checkout return validates ownership, requests reconciliation, and renders the current billing view. It never writes the tier directly. The UI may make one short reconciliation attempt, then shows an "Activating your plan" state that can finish without the browser.

Postgres membership state is the desired paid-seat truth. Member and role changes commit locally and durably mark the Workspace Billing Account due in the same transaction. The worker reads the latest desired quantity, reconciles the configured seat item, and verifies ambiguous provider responses by retrieving current subscription state. Foreground member UX no longer waits on Stripe. Transient retries coalesce to the newest seat count, while provider conflicts block only new billable additions and leave viewer access, demotions, removals, billing repair, and content download available.

The billing page shows the verified plan, subscription status, renewal or end date, paid-seat count, synchronization health, and the action the owner can take. It distinguishes current, activating, payment action required, restricted, retrying, and operator attention states. The Workspace retains its last verified access during provider outages. Explicit subscription policy governs trial, payment failure, cancellation, and recovery, so access and retention never depend on arrival order or error-message text.

## Implementation Decisions

- Add Workspace Billing Account to the domain glossary. It is the durable provider identity, current verified subscription snapshot, desired and synchronized paid-seat state, reconciliation health, and repair state for one Workspace. It is not the Stripe customer object, an invoice, or a generic Workflow Run.
- Record the ownership decision in an ADR. The Workspace Billing module owns billing synchronization through a small public interface for Checkout start, Checkout return observation, portal start, Stripe delivery acceptance, billing-state read, and due reconciliation. HTTP routes, React views, membership callers, and the worker do not reproduce subscription or recovery policy.
- Keep `Workspace.pricingTier` and `Workspace.status` as the access projection consumed by the rest of Narriflow. Only the Workspace Billing module may change that projection because of provider state. The Workspace Billing Account is the provider synchronization truth.
- Move customer ID, canonical subscription ID, seat item ID, interval, provider status, period end, cancellation flag, first past-due time, grace deadline, desired seats, synchronized seats, last verified time, next reconciliation time, attempt count, and repair state into the Workspace Billing Account.
- Remove user-level Stripe identity and billing-event ordering as billing inputs. Stop dual-writing personal User billing fields, remove the legacy Checkout interpretation that treats a user ID as a Workspace ID, and migrate remaining entitlement callers to Workspace pricing. Do not add compatibility reads for the retired pre-production shape.
- Extend durable webhook acceptance to Stripe. A unique provider and event-ID key makes exact redelivery idempotent. Store a normalized envelope containing event type, provider creation time, livemode, API version, customer, subscription, Checkout Session, Workspace hint, receipt time, and processing outcome. Do not persist the raw body, signature, payment details, billing address, or full Stripe object.
- Signature verification happens before durable acceptance through the Stripe adapter. An invalid or missing signature returns a typed client error. A valid new event that commits returns success after reconciliation is queued. A duplicate accepted event returns success without another side effect. A database failure before acceptance returns a server error so Stripe retries.
- Listen only to events needed to wake reconciliation and explain billing health. This includes Checkout completion and delayed-payment outcomes, subscription creation, update, pause, resume, and deletion, invoice payment success and failure, and relevant customer changes. Event payloads identify subjects and provide audit evidence; they do not directly set entitlements.
- Reconciliation retrieves current provider customer and subscription state. It does not compare `event.created` values to choose a winner. Provider-effective payment, trial, period, cancellation, and status facts establish transition timing; local receipt time and a global last-event timestamp do not.
- Validate the complete billing catalog once at web and worker startup. Every paid base price maps to exactly one tier and interval, every Business seat price maps to exactly one interval, no ID appears in more than one role, required values are present for enabled flows, and numeric worker limits are finite and bounded. An unmapped provider price leaves prior verified access unchanged and moves the account to operator attention.
- Prevent new multiple-subscription states. Checkout is available only when the Workspace has no entitlement-bearing subscription or is still pending its first payment. Existing paid Workspaces use a configured Stripe customer portal catalog for upgrades, downgrades, interval changes, payment methods, invoices, and cancellation.
- If reconciliation discovers multiple entitlement-bearing subscriptions, preserve the highest verified paid entitlement to avoid accidental access loss, select no destructive repair automatically, and mark operator attention. The owner sees a neutral billing-attention message and a portal action. Diagnostics identify provider object classes but never expose raw IDs to members.
- Subscription status policy is explicit. `trialing` and `active` grant the mapped paid tier. `incomplete` grants nothing for a new Workspace and remains pending payment. `past_due` preserves the last verified paid tier for seven days from the first durable observation, marks payment action required, and never resets that deadline on repeated events. `unpaid`, `paused`, `incomplete_expired`, and `canceled` grant no paid tier. A `cancel_at_period_end` subscription remains entitled through its active period and displays its end date.
- At the end of the past-due grace period, a still-past-due Workspace loses paid entitlement. A personal Workspace becomes active on Free. A collaborative Workspace that still has non-owner members becomes restricted on Free, preserving owner billing, view, and download access while blocking processing, publishing, API use, and new billable collaboration until payment or membership is resolved.
- A verified recovery to `active` or `trialing` restores the mapped tier and normal Workspace status. Existing role policy still applies. Recovery clears only unexpired retention deadlines and cannot restore a Project whose accepted deadline has passed.
- Apply the billing snapshot, Workspace tier and status projection, project-retention transition, and append-only billing transition in one transaction. The transition records previous and next plan, Workspace status, provider status, reason, effective time, observed time, and normalized source identifiers. Replays that produce no change do not append duplicate transitions.
- Preserve the accepted retention contract. A verified paid transition effective before a Project deadline clears that unexpired deadline. A paid-to-Free transition assigns the downgrade policy once at the provider-effective loss-of-entitlement time. Delivery replays, repair retries, and repeated past-due observations cannot extend retention.
- Checkout start uses a durable attempt with a client idempotency key stored before the first browser request. Workspace, target tier, interval, catalog version, and return destination are immutable. Reuse with different inputs returns a typed conflict. A lost response returns the same live Checkout Session or a stable terminal result.
- Customer provisioning is a durable phase inside Checkout start. Create through a stable provider idempotency key and bind the result to the Workspace Billing Account. After an ambiguous response, retry the same operation while the provider key is valid, then reconcile exact Workspace metadata before considering any new create. Multiple matching customers move to operator attention rather than automatic merge or deletion.
- Checkout return observation verifies that the session belongs to the current Workspace and attempt, records the session outcome, and requests immediate reconciliation. It returns a billing view with `activating`, `current`, `payment_action_required`, or `failed` rather than applying a tier from the session. The browser may poll with server `Retry-After` guidance and bounded jitter, and it may leave safely.
- The billing read model exposes only product facts: verified plan, interval, provider status translated to product language, renewal or end date, grace deadline, desired and synchronized additional seats, synchronization health, last successful sync, and allowed owner actions. It does not expose provider IDs, event IDs, raw errors, attempt IDs, or internal retry counts.
- Postgres membership roles are desired seat truth. Additional seat quantity equals current Admin and Editor memberships, excluding the owner; Viewers do not count. Invite creation does not bill. Invite acceptance into a billable role, role promotion or demotion, member removal, and concurrent mutations calculate from committed membership state.
- Membership mutations and a durable "billing synchronization due" marker commit in the same transaction. Foreground membership requests do not call Stripe. A recurring reconciliation schedule remains a backstop if a caller fails before an immediate wake-up signal.
- Seat reconciliation reads desired membership count and current provider subscription items after the claim. It identifies the seat item by the configured interval-specific seat price rather than trusting a stale local ID. It creates, updates, or removes only that known item. Every create or update uses a durable operation key; ambiguous results are resolved by retrieving current subscription state before another mutation.
- A stale seat attempt cannot settle synchronized quantity or health after its lease is lost. Rapid member changes can cause an older provider call to finish, but the next claimed attempt reads the newest desired count and converges again. Provider state is never treated as membership truth.
- A transient seat failure keeps member state and existing access, schedules retry, and shows synchronization in progress to the owner. An unknown price, multiple matching seat items, multiple subscriptions, or customer mismatch marks attention and blocks new billable-role additions. Viewer invitations, demotions, removals, portal access, and repair reconciliation remain available.
- Due reconciliation uses an immutable attempt ID and expiring lease. Every durable settlement checks the attempt. Work is ordered by `nextReconcileAt` and a stable identifier, not Workspace update time. Defaults are a batch of 25, concurrency four, bounded provider-operation deadlines, exponential backoff with jitter, and a finite per-attempt provider-call budget.
- Current accounts receive a periodic safety reconciliation through per-account due timestamps. Recently changed, activating, past-due, retrying, and seat-dirty accounts use shorter schedules. Attention accounts retry slowly enough to detect manual repair without consuming an unbounded provider budget. Pagination or keyset claiming must reach every due account.
- One account failure never stops the rest of a batch or the worker's other loops. The web path may make one short inline reconciliation attempt after Checkout return, then releases correctness to durable worker processing.
- Errors are typed as authentication, authorization, configuration, conflict, retryable provider, ambiguous provider, permanent provider, payment action required, and operator attention outcomes. HTTP and UI mapping use codes and result variants, never message comparison.
- Structured logs follow the repository JSON convention. Record Workspace, delivery type, claim, phase, provider operation class, attempt number, desired and observed seat counts, status transition, disposition, elapsed time, and next retry. Never log signatures, raw webhook bodies, API keys, customer email, billing address, payment details, Checkout URLs, portal URLs, or raw provider errors.
- Metrics cover accepted and duplicate deliveries, acceptance latency, queue age, reconciliation latency, retry and attention counts, stale settlements, customer conflicts, subscription conflicts, desired-versus-synchronized seats, grace-window entries and recoveries, Workspace restrictions, and retention transitions.
- Billing and member UX follows Blueline structure and tokens. Use one solid action per view, shared date formatting, accessible status text, non-toast persistent activation state, and focus-safe portal or retry actions. Replace hardcoded seat-price confirmation copy with the validated shared billing catalog.
- Migrate existing workspace billing identities into Workspace Billing Accounts, verify uniqueness and catalog mappings, then remove retired workspace provider columns and user-level billing dual writes as part of the pre-production cutover. Apply pending migrations before code that requires the new shape. Do not retain old webhook handling, direct tier application, old seat synchronization, or hidden fallback paths.
- Develop and verify provider-mutating behavior in Stripe sandbox. The cutover requires a configured portal catalog, registered event set, current webhook secret, worker billing configuration, and an operator repair runbook before any live-mode use.

## Testing Decisions

- The public Workspace Billing interface is the highest and primary behavior-test seam. Tests accept deliveries, start and resume Checkout, observe returns, open the portal, read billing state, mark membership changes, and reconcile due accounts through that interface.
- Good tests assert observable results: durable delivery acceptance, returned billing views, Workspace tier and status, retention deadlines, membership access, provider operations, synchronization health, audit transitions, retry scheduling, and diagnostics. They do not assert private helper calls, query ordering, raw Stripe object shapes, or React effect order.
- Deterministic interface tests use a fake Stripe adapter, manual clock, failure-injectable persistence adapter, recording diagnostics, and fixed billing catalog. They cover every failure point before and after provider calls and durable transitions.
- Delivery tests cover missing and invalid signatures, exact duplicate event IDs, separate events for the same object and type, equal-second creation, every event permutation, ignored types, database failure before acceptance, process termination after acceptance, and replay after successful settlement.
- Reconciliation tests cover active, trialing, incomplete, past-due grace, grace expiry, payment recovery, unpaid, paused, incomplete-expired, cancellation at period end, terminal cancellation, reactivation, provider timeout, unknown price, customer mismatch, missing metadata, multiple subscriptions, and no subscription.
- Retention tests run through the billing interface and prove pre-deadline upgrade rescue, post-deadline non-restoration, one-time downgrade assignment, repeated past-due observation without deadline extension, payment recovery, and atomic rollback of projection plus retention.
- Checkout and customer tests cover concurrent starts, idempotency replay, immutable-input conflict, lost provider response, lost database bind, expired Checkout Session, wrong Workspace return, delayed payment, abandoned Checkout, customer metadata recovery, and multiple-customer attention.
- Seat tests cover owner-only Workspace, viewer-only additions, Admin and Editor additions, invitation acceptance, concurrent promotions and removals, rapid count changes, first-item creation race, interval-specific price selection, zero-seat removal, lost provider responses, stale attempt settlement, duplicate items, payment failure, and recovery to the latest desired count.
- Disposable PostgreSQL tests drive the same module interface and prove unique event acceptance, one Workspace Billing Account, transaction rollback, lease claim and takeover, stale fencing, due-order fairness beyond one batch, append-only transition idempotency, concurrent Checkout attempts, and membership plus due-marker atomicity.
- Stripe sandbox adapter contracts verify raw-body signature construction, configured API version behavior, customer create and metadata lookup, Checkout create and retrieve, portal sessions, subscription listing and retrieval, status and cancellation fields, invoice payment evidence, idempotent create and update calls, seat item create/update/delete, and ambiguous-response recovery.
- Hono contract tests prove fast 200 acceptance for new and duplicate valid deliveries, 400 invalid signature, 500 pre-acceptance database failure, typed Checkout and portal mappings, owner authorization, strict validation, and `Retry-After` on activation polling.
- React tests assert current, activating, retrying, payment-action, restricted, and attention copy; owner and non-owner controls; renewal and grace dates; paid-seat counts; accessible announcements; focus behavior; one solid action; and absence of false success toasts or provider internals.
- Worker tests prove billing reconciliation runs independently of ingest, Workflow Run, Upload Session, retention, notification, and social loops. One slow or failed account cannot block later accounts, and keyset claiming eventually processes work beyond the first batch.
- Migration tests start from the current pre-production schema, migrate existing personal and collaborative Workspace billing identities, reject duplicates or unmapped catalog data, verify direct cutover, and prove no caller reads retired user or Workspace provider fields afterward.
- Final verification uses uncached focused suites, disposable PostgreSQL, Stripe sandbox contracts, repository typecheck, lint, tests, production build, full migration deploy chain, and a real-browser Checkout and portal checklist. The architecture recommendation is not marked complete from helper tests alone.

## Out of Scope

- Building a custom card form, invoice viewer, tax system, refund workflow, coupon manager, revenue-recognition ledger, or payment processor. Stripe Checkout and the customer portal remain the hosted payment interfaces.
- Automatically canceling, merging, refunding, or deleting duplicate Stripe customers or subscriptions. Detection and safe operator repair are in scope; destructive financial repair is not.
- Usage-based billing, metered processing minutes, prepaid credit packs, overage charging, seat volume discounts, or a new pricing model.
- Changing the accepted Free-project retention durations, purge workflow, backup policy, or restoration rules.
- Redesigning Workspace roles or transferring Workspace ownership.
- Adding an operator dashboard beyond structured diagnostics, metrics, repair commands, and the owner-facing attention state.
- Migrating historical billing data from a production system. Narriflow has no production billing data under the current pre-production policy.
- Generalizing the billing reconciliation mechanism into a repository-wide distributed transaction or job framework.
- Implementing the feature in this specification task. Each approved ticket is built separately.

## Further Notes

- Stripe documents that webhook deliveries may be duplicated and delivered out of order, and recommends asynchronous processing with durable duplicate handling: https://docs.stripe.com/webhooks
- Stripe's subscription guidance distinguishes `trialing`, `active`, `incomplete`, `past_due`, `unpaid`, `paused`, and `canceled`; Narriflow's seven-day past-due grace is an explicit product policy layered on those provider facts: https://docs.stripe.com/billing/subscriptions/webhooks
- Stripe requires Checkout fulfillment to be safe under repeated and concurrent calls and still requires webhooks even when the return page also triggers fulfillment: https://docs.stripe.com/checkout/fulfillment
- Stripe documents idempotency keys for safely retrying create and update requests. Keys can be removed after at least 24 hours, which is why Narriflow also needs durable operation state and provider reconciliation: https://docs.stripe.com/api/idempotent_requests
- Stripe's customer portal is the supported hosted interface for payment methods, invoices, subscription changes, and cancellation, and its changes still arrive through webhooks: https://docs.stripe.com/customer-management/integrate-customer-portal
- Stripe applies quantity changes with proration, while pending updates and payment behavior have separate constraints. Narriflow therefore treats committed membership as desired seat truth and handles payment health through subscription reconciliation rather than rolling membership backward from a provider error: https://docs.stripe.com/billing/subscriptions/quantities and https://docs.stripe.com/billing/subscriptions/pending-updates
- The past-due grace period, highest-entitlement handling for accidental multiple subscriptions, and non-blocking member mutation are Narriflow product decisions. They are not Stripe defaults.
- Implementation should follow the local dependency-ordered tickets. Each ticket starts in a fresh task with test-driven development and ends with Standards and Spec review plus uncached verification.
