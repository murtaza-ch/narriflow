# Deepen authenticated request policy

**Status:** ready-for-agent

## Problem statement

People using Narriflow expect the same request to receive the same access decision and a useful recovery path regardless of whether it reaches a Hono route, a Server Action, a server-rendered page, or the workflow event stream. Today those adapters reconstruct signed-in actor resolution, active Workspace selection, Workspace capability checks, Project access, Project lifecycle checks, input validation, and error translation themselves.

The repetition has already produced conflicting behavior. Some Project mutations pass through a generic `content.edit` middleware before checking their real capability. A processing, publishing, or download operation can therefore be admitted or refused for the wrong reason. The Project middleware performs access work that many handlers repeat. Extracted route modules still repeat authentication and validation. Server Actions throw generic message strings or return raw exception messages. The workflow stream authorizes once with one policy and later rechecks with a weaker one.

Identity is also ambiguous. The current Workspace request helper rewrites a generic user `id` to mean the Workspace owner while exposing the signed-in person separately as `actorUserId`. Callers use both values, sometimes in the same operation. A future maintainer cannot tell whether a service argument records the person who acted, scopes Workspace data, or preserves an old personal-owner key. This is a security and audit risk, not just naming debt.

The user-facing result is uneven. An expired session, a role change, a restricted Workspace, a missing Project, a stale active Workspace, invalid input, a retryable conflict, and an internal failure can collapse into the same generic error. Some clients discard the attempted input. Others log a status without giving the user a next step. Some expected errors leak implementation messages. Adding a new authenticated route requires copying enough policy that an omission can expose data or block a valid user.

## Solution

Introduce one deep Authenticated Request Policy module for browser-session requests. Every authenticated Hono handler, Server Action, server-rendered page admission, and workflow stream admission will cross one execution interface. The caller will declare the exact Workspace capability, an optional active Project requirement, optional untrusted input and its schema, and the domain operation. The module will resolve the signed-in actor and active Workspace, enforce the declared capability, resolve Project access and lifecycle once, validate input in a fixed order, run the operation, and return a typed success or expected failure.

The interface will return an unambiguous Actor Scope. The signed-in user ID always identifies the person who acted. Workspace identity, role, status, tier, and owner identity are named separately. No generic `id` may change meaning. Authenticated call paths and the service interfaces they invoke will use actor and Workspace identity explicitly. Narriflow's pre-production policy applies, so the cutover will not retain a dual request helper, aliased owner identity, string-error fallback, or shadow policy.

Hono, Server Actions and pages, the workflow event stream, and browser failure presentation remain thin adapters. They translate the same typed failures into their native response forms without recreating authorization or error policy. Successful response shapes and established domain behavior stay unchanged. Expected failures use stable machine codes, user-safe messages, correct status or action outcomes, bounded validation details, retry metadata where applicable, and a request identifier for support. Unexpected exceptions are logged with safe structured context and never sent to the browser verbatim.

## User stories

1. As a signed-out visitor, I want an authenticated browser request to tell me that sign-in is required, so that I can resume the intended task after signing in.
2. As a signed-in user whose session expires during a task, I want my attempted input preserved, so that signing in again does not force me to recreate the work.
3. As a signed-in user, I want a safe return destination carried through sign-in, so that recovery cannot redirect me to an untrusted site.
4. As a deleted or deactivated user, I want authenticated operations refused consistently, so that a stale Clerk session cannot access Narriflow data.
5. As a Workspace member, I want every request scoped to a membership validated by the server, so that an active-Workspace cookie is never treated as proof of access.
6. As a user whose saved active Workspace is no longer available, I want Narriflow to select an available Workspace and explain the change, so that I do not see unrelated missing-resource errors.
7. As a user with more than one Workspace, I want a link to a Project in another Workspace I belong to to offer a safe Workspace switch, so that shared links do not look broken.
8. As a user without access to another Workspace, I want its resource identifiers concealed as missing, so that requests do not disclose cross-Workspace existence.
9. As a Workspace Viewer, I want read and download operations to remain available where my role permits them, so that a generic write gate does not block valid work.
10. As a Workspace Viewer, I want edit, processing, publishing, brand, social, API, and management operations refused with a clear permission message, so that I know the action requires a different role.
11. As a Workspace Editor, I want each operation checked against its exact capability, so that publishing or social-account administration is not inferred from a generic edit permission.
12. As a Workspace Admin, I want permitted management actions to work without owner-only checks leaking into unrelated routes, so that my assigned role behaves consistently.
13. As a Workspace owner, I want billing-only recovery actions to remain available while the Workspace is pending payment or restricted, so that I can restore access.
14. As a non-owner in a restricted Workspace, I want a clear explanation that the Workspace owner must resolve billing, so that I do not keep retrying an action I cannot repair.
15. As a user, I want read-only access preserved when the current Workspace status permits it, so that a restriction does not hide content unnecessarily.
16. As a user opening a missing Project, I want a not-found state with a route back to Projects, so that I can continue using the app.
17. As a user opening an expired or purging Project, I want it treated as unavailable everywhere, so that one adapter cannot expose data another adapter hides.
18. As a user who loses Project access while a page is open, I want the next operation to stop and explain the change, so that stale UI cannot continue acting with old permissions.
19. As a user following a Project link from the wrong active Workspace, I want Narriflow to distinguish a recoverable Workspace mismatch from a Project I cannot access, so that it can offer the right next step safely.
20. As a user, I want a nested Clip, export, Social Post, dub, Brand Template, or audio asset to remain scoped by its owning domain module, so that request admission cannot be used to cross resource ownership.
21. As a user, I want a resource deleted between admission and mutation to return a stable missing or conflict outcome, so that a race does not become an internal error.
22. As a user, I want malformed JSON rejected before domain work begins, so that a broken request cannot cause a partial action.
23. As a user, I want unknown or forged input fields rejected by strict schemas, so that clients cannot smuggle infrastructure or ownership values into an operation.
24. As a user correcting a form, I want field-level validation issues attached to stable paths, so that the interface can focus or describe the invalid controls.
25. As a user, I want validation failures to preserve my submitted values, so that correction is quick and safe.
26. As a user, I want authentication and authorization checked before expensive request work, so that anonymous or forbidden callers cannot consume domain resources.
27. As a user, I want rate-limited operations to say when retrying becomes useful, so that the interface can show a bounded wait instead of a vague failure.
28. As a user, I want retryable provider or storage outages distinguished from validation and permission failures, so that retry is offered only when it can help.
29. As a user, I want revision and idempotency conflicts distinguished from temporary outages, so that I can refresh, reconcile, or retry the exact intent safely.
30. As a user, I want quota and plan-limit failures to keep their existing upgrade or usage recovery path, so that a deeper request policy does not flatten product guidance.
31. As a user, I want a known domain failure to have the same code and message across Hono and Server Actions, so that the same operation does not tell two stories.
32. As a user, I want unexpected server failures to show a safe message and support identifier, so that I can report the problem without seeing implementation details.
33. As a user, I want a successful operation to keep its current status, result shape, redirect, and revalidation behavior, so that the policy cutover does not disturb normal flow.
34. As a user, I want duplicate button presses and replayed requests to retain each domain module's existing idempotency rules, so that request-policy work does not create a second owner for replay behavior.
35. As a user watching processing progress, I want the workflow stream admitted by the same Project policy as the page, so that streaming cannot bypass lifecycle or Workspace rules.
36. As a user whose session, membership, capability, or Project access changes during a workflow stream, I want the stream to stop with a safe control outcome, so that stale access is not held indefinitely.
37. As a user whose workflow stream closes after access loss, I want the page to present the matching sign-in, permission, Workspace-switch, or unavailable state, so that a silent reconnect loop does not hide the cause.
38. As a support operator, I want a request identifier shared by safe client failures and structured logs, so that I can investigate without asking for private payloads.
39. As a security reviewer, I want unexpected exception text, stack traces, provider bodies, tokens, cookies, and submitted content excluded from responses and routine logs, so that failures do not leak secrets or user data.
40. As a maintainer, I want every authenticated entry point to declare a capability explicitly, so that a new route cannot inherit a permissive default accidentally.
41. As a maintainer, I want read and mutation capability to be declared by product intent rather than inferred from the HTTP method, so that specialized permissions remain correct.
42. As a maintainer, I want one Actor Scope type whose user ID always means the signed-in person, so that audit and ownership arguments cannot be swapped silently.
43. As a maintainer, I want active Workspace selection, membership, status, and capability resolved once per ordinary request, so that handlers do not repeat database work.

48. As a maintainer, I want adapter tests limited to transport translation, so that business rules do not return to Hono, Server Actions, pages, or browser components.
49. As a maintainer, I want table-driven policy tests to cover the full decision matrix, so that a policy change is verified once for every adapter.

51. As a maintainer, I want current domain module tests to remain authoritative for quotas, idempotency, persistence, rendering, billing, publishing, and upload lifecycles, so that request tests do not duplicate business behavior.
52. As a maintainer, I want old policy helpers and shallow duplicate tests deleted as each request family moves, so that the codebase never has two active policy owners.
53. As a maintainer, I want a final inventory of authenticated routes, actions, pages, and streams, so that direct actor resolution and handwritten authorization responses cannot remain unnoticed.
54. As a maintainer, I want public webhooks and token-based integrations explicitly outside the browser-session policy, so that incompatible authentication systems are not forced through one interface.
55. As a product owner, I want the migration delivered in independently verifiable request families, so that each slice can ship green and preserve completed architecture work.

## Implementation decisions

- Add Authenticated Request Policy to the project language. It is the browser-session application module that owns request admission, Actor Scope resolution, Workspace capability, optional active Project scope, input validation sequencing, and expected-failure normalization. It does not own domain business rules or transport rendering.
- The module has one public execution interface. A request declaration contains an explicit admission requirement, optional untrusted input plus a strict schema, optional rate-limit admission metadata, and the operation to run with validated input and Actor Scope.
- Admission requirements are explicit variants for signed-in actor, Workspace capability, and active Project plus Workspace capability. There is no default capability. HTTP methods do not imply capability.
- Actor Scope contains the signed-in App User and separately named Workspace context. The signed-in user ID always identifies the actor. Workspace ID, Workspace owner user ID, role, status, tier, and personal-Workspace status remain separate facts. The interface does not expose an aliased generic ID.
- Migrate authenticated call paths to actor and Workspace scoped service interfaces. Where a current service still accepts an owner-key argument, migrate the invoked interface or name the ownership fact explicitly during the same slice. Do not preserve the current request-level owner-ID alias or add a second compatibility helper.
- Resolve the provider session and Narriflow App User before Workspace selection. A missing provider session, deleted App User, or provider user that cannot resolve to a current App User produces `authentication_required`.
- Validate the active-Workspace cookie only as a selection hint. Resolve a current membership before constructing Actor Scope. If the saved selection is invalid but another Workspace is available, choose the established fallback and return enough safe state for the app shell to explain that the Workspace changed. Never authorize from the cookie value alone.
- Enforce Workspace status and the exact declared capability before Project lookup or domain work. Distinguish role denial from status denial internally so browser adapters can direct an owner to billing and tell other members to contact an owner. Both remain authorization failures at the transport.
- Resolve an active Project with one Workspace-scoped query that includes expiry and purge lifecycle rules. A Project that is absent, expired, purging, or belongs to a Workspace the actor cannot access is concealed as `project_not_found`.
- When a Project belongs to another Workspace in which the actor has a current membership, return a typed `active_workspace_mismatch` without performing the operation. The failure may expose only the Workspace identity and display name the actor is already entitled to see. Browser adapters offer an explicit switch and retry. They do not switch Workspace during a mutation automatically.
- A successful Project admission is not a durable authorization token. Domain modules continue to scope nested-resource reads and writes by Actor Scope, Workspace, Project lifecycle, revision, and transaction invariants where applicable. The request policy does not weaken database-level ownership checks or absorb resource-specific authorization.
- Ordinary request execution caches provider, App User, Workspace, and Project resolution only within that request. It does not introduce process-global authorization caches. Long-lived streams use uncached reauthorization on the existing bounded heartbeat interval.
- The execution order is authentication, active Workspace resolution, capability, optional common rate limit, optional Project scope, input validation, then domain operation. Rate limiting may run before parsing only when its key can be derived from authenticated Actor Scope and the operation has already passed authorization.
- Strict schemas reject unknown fields where the existing domain contract is strict. Malformed bodies and schema failures do not call the domain operation. Validation details are bounded to field path, stable issue code, and user-safe message.
- Expected failures use a closed transport-neutral taxonomy that includes authentication required, Workspace selection changed, active Workspace mismatch, capability denied, Workspace restricted, missing resource, invalid input, semantic refusal, quota or payment refusal, conflict, rate limited, retryable unavailable, and accepted or pending work where a domain contract needs it.
- Domain modules retain their specific error codes and safe recovery metadata. Expected errors must expose a typed code and disposition. Request policy and adapters never branch on `Error.message`. Unknown exceptions are not converted into validation or authorization failures.
- Hono maps typed failures to stable JSON with `error` as the machine code, an optional user-safe `message`, bounded `issues` or `details`, and a request identifier. Existing clients may continue reading those fields. Successful response bodies and statuses remain unchanged.
- HTTP status policy is consistent: 400 for malformed or schema-invalid requests under current contracts, 401 for missing authentication, 403 for current-Workspace capability or status denial, 404 for concealed or unavailable resources, 409 for Workspace mismatch and state or revision conflicts, 402 for established quota or payment refusals, 422 for established semantic or integrity refusals, 429 for rate limits, 503 for retryable dependency failure, and 500 for unexpected failure.
- A 429 or a retryable accepted state includes a valid `Retry-After` header when the server can state a bounded delay. Browser copy never promises that an unknown provider failure will succeed on the next attempt.
- The HTTP error contract follows the useful parts of RFC 9457 without forcing a media-type migration on existing internal clients. Stable code, status, safe detail, request identity, and extension data stay consistent. Narriflow does not expose stack traces or raw exception messages.
- Server Action and page adapters map expected failures to serializable action results, safe redirects, `notFound()`, or explicit permission and Workspace recovery views. They must not catch framework redirect or not-found control flow as ordinary errors. Unexpected failures propagate to the nearest error boundary after structured logging.
- Shared browser failure presentation classifies the stable contract once. Authentication loss preserves the safe current destination. Permission loss keeps attempted values and removes unavailable actions after refresh. Missing resources offer navigation back to the relevant collection. Workspace mismatch offers a deliberate switch. Conflicts preserve intent and offer refresh or retry. Rate limits expose wait time. Temporary failures preserve intent and offer retry.
- Existing specialized browser modules may keep richer domain recovery, such as Upload Session resume or Studio conflict convergence, but they consume the common authentication, authorization, missing, rate-limit, and unavailable classifications instead of recreating them.
- The workflow event stream uses the same active-Project admission before opening. During the stream it re-evaluates session, membership, capability, Workspace status, and Project lifecycle without request-local caching. On revocation it emits one bounded safe control event when possible, closes, and lets the browser adapter present recovery. It never sends private denial details on the stream.
- Public health checks, Stripe and social-provider webhooks, Clerk webhooks, OAuth callbacks that must establish identity, MCP OAuth, and scoped API-key requests do not use this browser-session module. Their trust and replay models remain independent.
- Structured diagnostics follow the repository JSON convention. Record the request identifier, adapter kind, operation name, method where applicable, stable failure code, status, actor ID when resolved, Workspace ID when resolved, Project ID when declared, elapsed time, and disposition. Do not log cookies, tokens, raw bodies, validation values, signed URLs, provider responses, stack traces in user-facing payloads, or user content.
- Preserve existing successful HTTP, Server Action, page, and stream behavior while moving policy. Preserve completed Upload Session, Workspace Billing, Clip Editor Document Persistence, Studio Editing Session, Workflow Run, Clip Render Attempt, and Social Publication Attempt ownership. Request handlers remain adapters to those modules.
- Migrate by request family. A moved family cannot retain direct current-user resolution, handwritten capability or Project checks, raw message translation, or a second policy middleware. Remove the old implementation and redundant tests in the same ticket.
- Splitting the large route file is allowed only when it helps a vertical migration slice. File splitting by itself does not satisfy this spec because it moves repetition without deepening the module.
- The final cutover removes the compatibility Workspace App User shape, the generic active-Project middleware, direct authenticated adapter imports of the old helpers, string comparisons for request behavior, and handwritten `Unauthorized`, `Forbidden`, `Project not found`, and `Invalid payload` responses from migrated browser-session surfaces.
- No database schema change is required for the request policy itself. If a service interface migration uncovers a remaining pre-production owner-key data path, remove that path under the repository compatibility policy rather than adding a dual read or write.

## Testing decisions

- Authenticated Request Policy is the highest and primary test seam. Tests call its single execution interface and assert success values, typed failures, call ordering, and which dependencies did or did not run. Tests do not inspect helper calls or private state.
- Table-driven interface tests cover missing provider session, deleted App User, valid and stale Workspace selection, missing membership, every role and Workspace-status capability combination, exact capability declarations, active and unavailable Projects, inaccessible cross-Workspace Projects, authorized Workspace mismatch, malformed input, strict-schema rejection, common rate limits, typed domain failures, and unexpected exceptions.
- Ordering tests prove unauthenticated and forbidden requests perform no rate-limit, parse, Project, or domain work as applicable; Project failure performs no parse or domain work; invalid input performs no domain work; and each ordinary request resolves actor, Workspace, and Project at most once.
- Actor Scope tests prove the signed-in actor ID never changes meaning, Workspace owner identity cannot be substituted accidentally, and audit-aware service calls receive the actor and Workspace expected by the interface.
- Disposable PostgreSQL tests cover active-Workspace membership, role changes, restricted and pending-payment status, expired or purging Projects, cross-Workspace concealment, authorized Workspace mismatch, membership removal, and lifecycle changes between requests. They drive the public policy interface rather than testing repository helpers directly.
- The provider-session adapter has focused contract tests for signed-out, signed-in, stale provider identity, and deleted Narriflow user outcomes. No live Clerk dependency is required for the normal suite.
- Hono contract tests cover failure code, safe message, status, bounded issues, request identifier, `Retry-After`, absence of private exception text, and unchanged success responses. They use one representative route per failure shape rather than repeating the full policy matrix for every route.
- Server Action and page adapter tests cover serializable expected failures, safe sign-in return destinations, Workspace mismatch recovery, permission and restricted-Workspace presentation, `notFound()`, preserved form values, redirects and revalidation after success, and propagation of unexpected exceptions.
- Browser adapter tests cover session expiry, role loss, Workspace restriction, Workspace mismatch, missing resources, field issues, conflict, quota, rate-limit countdown, retryable unavailability, support identifiers, focus movement, and preservation of attempted values. Existing Upload Session and Studio tests remain authoritative for their richer resume and convergence behavior.
- Workflow stream tests cover initial policy refusal, one successful admission, revocation of session, membership, capability, Workspace status, Project access, expiry during an open stream, one safe control event, closure, and no reconnect loop with stale credentials.
- Domain module tests remain authoritative for business-specific decisions and persistence. Request-policy tests do not reproduce quota arithmetic, billing synchronization, upload verification, document revision planning, render recovery, publication recovery, or provider behavior.
- Replace, do not layer. Remove tests that only restate actor, capability, Project, validation, or error translation inside individual handlers after the equivalent behavior is covered through the policy interface. Keep small adapter tests where transport behavior differs.
- Each migration slice adds a representative success, authentication, authorization, validation, known domain failure, and unexpected-failure contract test for its adapter family before removing the old path.
- Final coverage includes an explicit inventory of browser-session Hono routes, Server Actions, server-rendered admissions, and long-lived streams. Public and non-session surfaces are allowlisted with their separate trust model. The inventory fails if a migrated surface resolves the current user or emits common authorization responses outside the approved adapters.
- Completion verification runs focused policy, adapter, browser, and PostgreSQL suites, followed by repository typecheck and tests. Because the web adapter changes broadly, final cutover also runs the affected build and lint commands even where lint scripts are currently no-ops.

## Out of scope

- Changing Clerk sign-in, sign-up, OAuth consent, account recovery, or webhook synchronization behavior.
- Unifying browser sessions with MCP OAuth, scoped API keys, provider OAuth callbacks, Stripe webhooks, Clerk webhooks, TikTok webhooks, or public share access.
- Replacing Workspace roles or capabilities, changing the capability matrix, or redesigning restricted and pending-payment product policy.
- Moving domain authorization, ownership, revision fencing, idempotency, quota, retention, upload, billing, rendering, dubbing, or publication rules into request policy.
- Changing successful response bodies, success status codes, redirects, revalidation, or established pending-result contracts.
- Converting Narriflow's internal browser endpoints into a public versioned API or requiring every client to adopt the `application/problem+json` media type.
- Adding automatic mutation-time Workspace switching. Users must confirm a Workspace change before a failed mutation is retried.
- Adding a global distributed authorization cache, capability version tokens, a policy language, role administration redesign, or a generic workflow engine.
- Splitting every route into a separate file when no vertical policy migration requires it.
- Preserving the ambiguous owner-ID request shape, direct message-based error handling, or parallel old and new policy implementations for compatibility.

## Further notes

- The architecture review measured 77 handlers and 67 catch blocks. The current main adapter has grown further and contains 77 direct actor resolutions, 38 Project-access calls, 24 explicit Workspace actor checks, 46 schema parses, and 70 catch blocks. The finding has strengthened since the report.
- RFC 9457 defines a standard problem-details model for HTTP APIs. Narriflow can adopt its stable, extensible failure semantics while retaining current internal JSON fields during the direct cutover: https://www.rfc-editor.org/rfc/rfc9457.html
- RFC 9110 defines the HTTP semantics for authentication, authorization, missing resources, conflicts, and temporary failures. RFC 6585 defines 429 Too Many Requests and its optional `Retry-After` guidance. Status alone is not enough for UX, so Narriflow pairs it with a stable code and recovery metadata: https://www.rfc-editor.org/rfc/rfc9110.html and https://www.rfc-editor.org/rfc/rfc6585.html
- Next.js recommends returning expected Server Action errors as values and reserving thrown exceptions for unexpected failures handled by error boundaries. The adapter design follows that split: https://nextjs.org/docs/app/getting-started/error-handling
- The generic Project middleware currently infers edit access from non-read HTTP methods, but Narriflow has separate processing, publishing, download, brand, social, API, member, Workspace, and billing capabilities. Explicit declarations are safer and easier to review.
- The established local tracker convention is used because this repository has no configured tracker document. Tickets will live beside this spec and use `ready-for-agent` status plus explicit blocking edges.
